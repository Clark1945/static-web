第 0 章先看全貌：為什麼要訊息佇列，RabbitMQ 長什麼樣

訊息佇列解決什麼問題

假設「使用者下單」要做：扣庫存、建立訂單、寄確認信、通知倉儲、累積點數、推播到 App。全部寫在同一個 HTTP 請求裡，會有幾個問題：

  • 耦合：下單服務要認識每一個下游，新增一個下游就要改下單程式。
  • 延遲與可用性：寄信服務慢或掛掉，整個下單就慢或失敗，但其實「寄信失敗」不該讓訂單失敗。
  • 尖峰：大促時流量是平常的幾十倍，下游扛不住。

訊息佇列的做法：下單服務只負責把「訂單已建立」這個事實丟進 broker，馬上回應使用者；各下游各自從 broker 取訊息、依自己的速度處理。得到的好處是解耦、非同步、削峰。

代價別忽略：系統變成最終一致；訊息可能重複，下游必須做到冪等；除錯要追蹤跨服務的訊息流；多了一個必須維運的基礎設施。呼叫端需要立刻拿到結果的流程（查餘額、登入驗證）通常不該用 MQ。

RabbitMQ 的核心模型

最容易誤解的一點：生產者不是直接把訊息送進 queue，而是送給 exchange，由 exchange 依規則決定要放進哪些 queue。

  1. Producer生產者，發訊息
  2. Exchange依規則分送
  3. Bindingexchange 與 queue 的規則（routing key）
  4. Queue暫存訊息
  5. Consumer消費者，處理後 ack
名詞說明
Connection應用程式與 broker 的一條 TCP 連線，建立成本高，應長期持有、重複使用
Channel一條連線內的輕量「虛擬連線」。幾乎所有操作（發、收、宣告）都在 channel 上做
Virtual host（vhost）邏輯隔離單位，類似資料庫的 schema。不同 vhost 的 exchange / queue / 權限互不相通
Exchange接收生產者訊息並路由。類型：direct、fanout、topic、headers
Queue儲存訊息、等待消費者取走的緩衝區
Binding連結 exchange 與 queue 的規則，可帶 binding key
Routing key生產者發訊息時附帶的字串，exchange 用它去比對 binding
Ack消費者告訴 broker「我處理完了，可以刪掉這則」
為什麼要多一層 exchange 讓生產者與消費者的拓撲脫鉤：生產者只管「發到 order.events」，之後多一個消費者，只要新增 queue 並綁定，生產者程式完全不用改。

RabbitMQ、Kafka、Redis 怎麼選

簡單的判斷：要「把工作交給別人做」並且每則訊息逐一確認 → RabbitMQ；要「保留所有事件的歷史、多個系統各自重播」→ Kafka。兩者常常並存。

      RABBITMQ_DEFAULT_PASS: app-secret

    restart: unless-stopped

volumes:
  rabbitmq-data:
docker compose up -d
# 開 http://localhost:15672，用 app / app-secret 登入
docker exec rabbitmq rabbitmq-diagnostics check_running

預設帳號 guest / guest 只允許從本機（localhost）連線，這是刻意的安全設計。正式環境必須自己建立使用者、給最小權限，並刪除或停用 guest（第 9 章）。

Spring Boot 的第一個範例

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: app
    password: app-secret
    virtual-host: /
@Configuration
public class HelloConfig {
    @Bean
    Queue helloQueue() {
        return QueueBuilder.durable("hello").build();   // 啟動時由 RabbitAdmin 自動宣告
    }
}
@Component
public class HelloDemo {
    private final RabbitTemplate rabbit;
    public HelloDemo(RabbitTemplate rabbit) { this.rabbit = rabbit; }

    // 送到預設 exchange（名稱為空字串），routing key = queue 名稱
    public void send() { rabbit.convertAndSend("", "hello", "Hello RabbitMQ"); }

    @RabbitListener(queues = "hello")
    public void receive(String body) { System.out.println("收到：" + body); }
}

這裡用到了 RabbitMQ 的一個特性：每個 queue 都會自動綁定到預設 exchange（名稱是空字串，類型 direct），binding key 就是 queue 名稱。所以「送到 "" + routing key 等於 queue 名」就等於直接送進該 queue。學習時很方便，但正式設計請使用具名 exchange（第 2 章）。

第 2 章Exchange 與路由

四種 Exchange

類型路由規則典型用途
directrouting key 與 binding key 完全相等才送依類別分派：log.error 到告警、log.info 到歸檔
fanout忽略 routing key，送給所有綁定的 queue廣播：快取失效通知、設定更新
topicrouting key 是以 . 分隔的單字，binding key 可用萬用字元事件路由：order.created.tw，各消費者訂閱感興趣的子集
headers比對訊息標頭而非 routing key很少用，topic 通常已足夠

topic 的萬用字元

  • *：剛好一個單字
  • #：零個或多個單字
binding keyorder.createdorder.created.tworder.paid.twpayment.failed
order.created✔✘✘✘
order.*✔✘（多一個單字）✘✘
order.#✔✔✔✘
*.*.tw✘✔✔✘
#✔✔✔✔
命名建議 routing key 用「領域.事件.（修飾）」，例如 order.created。exchange 以領域或服務命名（order.events），不要用消費者的名稱，否則生產者又和消費者耦合了。

用 Spring 宣告拓撲

@Configuration
public class OrderTopology {
    public static final String EXCHANGE = "order.events";

    @Bean
    TopicExchange orderExchange() {
        return new TopicExchange(EXCHANGE, true, false);       // durable, 非 auto-delete
    }

    // 寄信服務：只關心「訂單建立」
    @Bean
    Queue mailQueue() {
        return QueueBuilder.durable("order.created.mail").quorum().build();
    }
    @Bean
    Binding mailBinding(Queue mailQueue, TopicExchange orderExchange) {
        return BindingBuilder.bind(mailQueue).to(orderExchange).with("order.created");
    }

    // 稽核服務：訂單所有事件都要
    @Bean
    Queue auditQueue() {
        return QueueBuilder.durable("order.audit").quorum().build();
    }
    @Bean
    Binding auditBinding(Queue auditQueue, TopicExchange orderExchange) {
        return BindingBuilder.bind(auditQueue).to(orderExchange).with("order.#");
    }
}

發一則 order.created：寄信與稽核兩個 queue 都各收到一份獨立的副本；發 order.paid：只有稽核收到。每個 queue 內的消費者則是「競爭」關係：同一則訊息只會交給其中一個消費者。

找不到對應 queue 的訊息會被「默默丟掉」。如果 routing key 打錯、或 binding 還沒建立，broker 不會報錯，生產者也不會知道。兩個解法：發送時設定 mandatory 並處理 return（第 4 章）；或替 exchange 設定 alternate-exchange，把無法路由的訊息導到一個專門收集的 queue。

其他實用觀念

  • 宣告是冪等的：重複宣告同名同屬性的 exchange / queue 沒問題；但屬性不同（例如 durable 不同、queue 類型不同）會拋 PRECONDITION_FAILED，必須先刪除再重建。
  • 誰負責宣告：通常由消費者宣告自己的 queue 與 binding（它最清楚自己要什麼）；exchange 由擁有它的服務宣告。Spring 的 RabbitAdmin 會在連線建立時自動宣告所有 Bean。
  • Exchange 可以綁 exchange（exchange-to-exchange binding），用來組合複雜的路由，但會增加理解難度，謹慎使用。
  • 系統內建的 amq.* exchange 保留給系統使用，不要自己取這類名稱。

第 3 章Queue 類型與屬性

三種 Queue 類型

ClassicQuorumStream
複製只存在一個節點（4.0 起已移除鏡像佇列）Raft 共識，複製到多數節點複製，追加式日誌
資料安全節點掛掉，該 queue 不可用，訊息可能遺失多數節點存活就不會遺失已確認的訊息同左
消費後刪除刪除保留，可重複讀、從指定位置讀（Kafka 式）
適合暫存、可丟失的資料、單節點開發環境需要可靠與高可用的一般業務佇列（首選）需要重播、大量扇出、高吞吐
限制—一定是 durable、不可 exclusive；優先權支援有限；吞吐略低於 classic用法與 AMQP queue 不同（偏移量、需 prefetch）
// Spring：宣告 quorum queue
QueueBuilder.durable("order.created.mail").quorum().build();

// 或以 argument 指定
QueueBuilder.durable("q").withArgument("x-queue-type", "quorum").build();
建議 新專案的業務佇列預設用 quorum。要小心的是：queue 類型建立後不能更改，要換類型就得建新 queue、遷移訊息。

其他屬性（宣告時指定）

屬性說明
durablequeue 的定義是否在 broker 重啟後保留。正式環境的業務佇列都應 true。注意：queue 持久不代表訊息持久，訊息還要標記 persistent（第 4 章）
exclusive只限宣告它的那條連線使用，連線關閉就刪除。適合臨時回覆佇列
auto-delete最後一個消費者離開就自動刪除

x-expiresqueue 閒置多久後自動刪除
x-max-length / x-max-length-bytesqueue 長度 / 大小上限
x-overflow超過上限時：drop-head（預設，丟最舊的）或 reject-publish（拒絕新訊息，搭配 publisher confirm 產生 nack）

用 Policy 而非硬寫在程式裡

queue 的 argument 一旦宣告就不能改；Policy 則是由 broker 端依名稱模式套用，可隨時調整，不必改程式、重建 queue。TTL、長度上限、DLX 這類營運參數，建議用 policy 管理。

# 所有以 order. 開頭的 queue，訊息最多存活 1 小時、最多 10 萬則
docker exec rabbitmq rabbitmqctl set_policy order-limits "^order\." \
  '{"message-ttl":3600000,"max-length":100000}' --apply-to queues

當 policy 與 queue argument 衝突時，argument 優先（部分屬性取較小值）。

Queue 不是資料庫，也不是越大越好。長期堆積大量訊息會佔用記憶體與磁碟、拖慢 broker、延長故障後的恢復時間。把 queue 當成「暫時的緩衝」，堆積通常代表消費端出了問題，應當警報，而不是放任它長大。

第 4 章訊息可靠性：怎麼確保不丟、不重

「訊息不會丟」不是 RabbitMQ 預設就給你的，而是三個環節都要做對。任何一個環節有缺口，訊息就可能無聲消失。

  1. ① 生產者 → BrokerPublisher confirm + mandatory
  2. ② Broker 儲存durable queue（或 quorum）+ persistent 訊息
  3. ③ Broker → 消費者手動 / 受控的 ack + 處理失敗策略

① 生產者到 Broker

預設情況下，basicPublish 送出就算完成，不保證 broker 真的收到、也不保證路由成功。需要兩個機制：

  • Publisher Confirm：broker 收到並處理完（已寫入所有目標 queue；quorum queue 則是已複製到多數）後，回覆 ack；處理失敗回覆 nack。生產者非同步地接收這些確認。
  • mandatory + Return：訊息無法路由到任何 queue 時，broker 把訊息退回給生產者（basic.return）。注意此時 broker 仍會發 confirm ack（「我處理完了」，結果是沒地方放），所以兩者要一起用。
spring:
  rabbitmq:
    publisher-confirm-type: correlated    # 啟用 confirm，並帶回 CorrelationData
    publisher-returns: true
    template:
      mandatory: true
@Component
public class PublisherCallbacks {
    private static final Logger log = LoggerFactory.getLogger(PublisherCallbacks.class);

    public PublisherCallbacks(RabbitTemplate rabbit) {
        rabbit.setConfirmCallback((CorrelationData cd, boolean ack, String cause) -> {
            String id = cd != null ? cd.getId() : "unknown";
            if (ack) {
                log.debug("broker 已確認 {}", id);
            } else {
                log.error("broker 拒絕 {}：{}", id, cause);   // 應重送，或標記失敗讓補償機制處理
            }
        });
        rabbit.setReturnsCallback(returned ->
            log.error("無法路由：exchange={}, key={}, replyText={}",
                returned.getExchange(), returned.getRoutingKey(), returned.getReplyText()));
    }
}
public void publishCreated(OrderCreated evt) {
    CorrelationData cd = new CorrelationData(evt.orderId().toString());
    rabbit.convertAndSend("order.events", "order.created", evt, msg -> {
        msg.getMessageProperties().setMessageId(UUID.randomUUID().toString());   // 給消費端做冪等用
        return msg;
    }, cd);
}

confirm 是「非同步」的。convertAndSend 回傳不代表 broker 已確認。如果程式在 confirm 到達前就當作「發送成功」並提交資料庫交易，仍然可能丟訊息。真正嚴謹的做法是 Outbox（第 7 章）。AMQP 的交易模式（txSelect）雖然也能保證，但吞吐會掉到十分之一以下，實務上不建議使用。

② Broker 儲存

  • queue 必須 durable（quorum queue 一定是）。
  • 訊息要標記 persistent（delivery_mode = 2）。Spring AMQP 的 RabbitTemplate 預設就是 persistent，原生客戶端需自己設定。
  • Broker 並不是每則訊息都立刻 fsync；單節點的 classic queue 在 confirm 之前會先落盤，但硬體故障仍會遺失資料，這正是需要 quorum queue 把資料複製到多個節點的原因。

③ Broker 到消費者：Ack

動作意思結果
basicAck處理成功broker 刪除該訊息
basicNack(requeue=true)處理失敗，放回 queue訊息重新排到 queue（通常是原位置附近），可能馬上再被取走
basicNack / basicReject(requeue=false)處理失敗，不要了丟棄；有設 DLX 則進死信（第 6 章）
連線斷線 / channel 關閉未 ack 的訊息broker 自動把它們重新放回 queue（所以訊息會被重複投遞）

auto-ack（自動確認）會丟訊息。RabbitMQ 原生的 autoAck=true 是「一送出就當作已確認」；消費者拿到後如果當掉，訊息就永久消失。Spring AMQP 的 AUTO 模式不同：它是「listener 方法正常返回才 ack，拋例外就 nack」，是安全的。兩者名稱相似，意思完全不同。

無限重試的死循環。Spring 預設 default-requeue-rejected = true：listener 拋例外，訊息被放回 queue，立刻又被取走、又拋例外…，CPU 與 log 瞬間爆滿，而且這則「毒藥訊息」會卡住後面的訊息。一定要設計失敗處理（第 6 章）。

Prefetch：一次預取幾則

Broker 不會等消費者處理完一則才發下一則，而是一次最多派送 prefetch 則「未確認」的訊息給該消費者。

  • prefetch 太小（例如 1）：每則都要等一次網路往返，吞吐低。
  • prefetch 太大：一個慢消費者囤積大量訊息，其他消費者閒置，負載不平均；消費者當掉時，大量訊息要重新投遞。
  • 經驗：處理很快（毫秒級）可設 50～250；處理很慢（秒級以上、需要公平分配）設 1～10。Spring 預設 250。

「剛好一次」並不存在

在分散式系統中，要同時保證不丟（at-least-once）與不重（at-most-once）是做不到的。RabbitMQ 實務上的選擇是 at-least-once（至少一次）：寧可重複，也不遺失。因此：

結論：消費端必須冪等。同一則訊息被處理兩次，結果要和處理一次一樣。具體做法見第 5 章。

consumer_timeout 消費者拿到訊息後，若超過 30 分鐘（預設）還沒 ack，broker 會關閉該 channel，訊息重新投遞。長時間任務要不是拆小、就是調高 consumer_timeout。

練習 4-1：可靠性檢查清單

看參考答案

  2. Broker：exchange、queue 都 durable；queue 用 quorum；訊息 persistent；叢集至少三個節點。
  3. 消費者：使用 AUTO（或手動）ack，處理成功才確認；設定有限次數的重試 + 死信佇列，避免毒藥訊息；以 messageId 做冪等去重，寄信前先檢查是否已寄。
  4. 監控：queue 堆積、DLQ 有訊息、unacked 長時間不下降都要告警。

第 5 章Spring AMQP 實戰

連線與 Channel 管理

  • CachingConnectionFactory（Spring Boot 預設）只建立一條連線，並快取 channel 重複使用。不要自己每次發訊息都 new 一條連線，這是最常見的連線洩漏來源（第 9 章）。
  • Channel 不是執行緒安全的（尤其在發布 confirm 時）。RabbitTemplate 會從快取取出 channel 使用後歸還，因此 template 本身可以安全共享。
  • 生產與消費建議使用不同的連線（Spring 預設已分開），避免 broker 因流量控制阻塞發布連線時，連帶影響消費。

訊息序列化：用 JSON

三個要想清楚的設定

設定影響
concurrency同一個 listener 的消費者執行緒數，會打破單一 queue 的順序保證。要保序就設為 1
prefetch每個消費者執行緒最多持有的未確認訊息數。總未確認數 ≈ 執行緒數 × prefetch
acknowledge-modeauto（簡單，推薦）、manual（自行控制 ack 時機）、none（相當於 auto-ack，會丟訊息，不要用）

手動 Ack：需要時才用

@RabbitListener(queues = "order.created.mail", ackMode = "MANUAL")
public void handle(OrderCreated evt, Channel channel,
                   @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        service.process(evt);
        channel.basicAck(tag, false);
    } catch (TemporaryException e) {
        channel.basicNack(tag, false, true);     // 暫時性錯誤：放回去再試（要小心死循環）
    } catch (Exception e) {
        channel.basicNack(tag, false, false);    // 永久性錯誤：丟棄，進 DLQ
    }
}

手動 ack 的風險是「忘了 ack」：訊息一直卡在 Unacked，直到連線關閉或超過 consumer_timeout。能用 auto 搭配重試與 DLQ 解決的，就不要手動。

冪等消費

因為至少一次的語意，同一則訊息可能到達多次。常見做法：

做法說明
天然冪等「把狀態設為 PAID」做幾次都一樣；用 UPDATE ... SET status='PAID' 而非 amount = amount + x
唯一鍵去重以 messageId（或業務唯一鍵）寫入「已處理表」，唯一索引衝突就代表處理過了
條件更新（樂觀鎖）UPDATE ... WHERE id=? AND version=?，影響行數為 0 就跳過
Redis SETNX + TTL輕量，但與資料庫交易不是原子，要注意失敗時的回滾
@Transactional

    try {
        processedRepo.insert(messageId);          // processed_message.message_id 有 UNIQUE 約束

        return;                                   // 已處理過：直接當成功，讓外層 ack
    }
    mailGateway.send(evt.email(), "訂單成立", renderBody(evt));
}

注意這段的盲點：「寫入已處理表」與「寄信」不是同一個原子操作。若寄信成功但交易回滾（或反過來），仍會有重複或遺漏。寄信這類外部副作用最好本身也支援冪等鍵（例如帶 idempotency key 呼叫郵件服務），或接受「極少數情況重複寄一封」的取捨。

順序性

  • 單一 queue、單一消費者、不使用 requeue：嚴格 FIFO。
  • 多消費者並行處理：先出的不一定先完成，順序無法保證。
  • nack(requeue=true)：被放回的訊息會排回原位置附近，但消費者已處理了後面的訊息，順序已被打亂。
  • 需要「同一個訂單的事件依序處理，但不同訂單並行」：使用 Single Active Consumer（x-single-active-consumer，同一 queue 同時只有一個消費者運作，其他待命）搭配多個 queue；或用 Consistent Hash Exchange 外掛，依 key 分流到多個 queue，每個 queue 單消費者。

第 6 章死信（DLX）、重試與延遲訊息

死信交換器（Dead Letter Exchange）

訊息在以下情況會變成「死信」，被轉送到該 queue 設定的 DLX：

  • 消費者 reject / nack 且 requeue=false
  • 訊息 TTL 到期
  • queue 長度超過上限（drop-head 溢出時被擠掉的訊息）
  • quorum queue：投遞次數超過 x-delivery-limit

DLX 就是一個普通的 exchange，死信被當成新訊息發給它，可以綁定一個 DLQ（死信佇列）集中收集失敗訊息。訊息的 x-death 標頭會記錄原因、來源 queue、次數，方便排查。

@Configuration
public class DeadLetterTopology {

    @Bean DirectExchange orderDlx() { return new DirectExchange("order.dlx", true, false); }

    @Bean Queue mailDlq() { return QueueBuilder.durable("order.created.mail.dlq").quorum().build(); }

    @Bean Binding mailDlqBinding() {
        return BindingBuilder.bind(mailDlq()).to(orderDlx()).with("order.created.mail");
    }

    @Bean Queue mailQueue() {
        return QueueBuilder.durable("order.created.mail").quorum()
            .deadLetterExchange("order.dlx")
            .deadLetterRoutingKey("order.created.mail")
            .deliveryLimit(5)                 // quorum 專用：最多被投遞 5 次
            .build();
    }
}

DLQ 一定要有人看。DLQ 有訊息代表有業務需要處理的失敗：設告警；提供「修正後重新投遞」的工具（例如把 DLQ 的訊息 shovel 回原 queue，或寫一個管理頁面）；不要讓它變成沒人看的垃圾桶。

重試策略比較

方案做法優點缺點
A. Spring 內建重試retry.enabled，在消費者執行緒內 sleep 後重試簡單重試期間佔住執行緒與訊息，降低吞吐；程式重啟時計數歸零
B. 等待佇列（wait queue）失敗 → 送到無消費者、帶 TTL 的等待 queue，到期經 DLX 回主 queue非阻塞；延遲由 broker 計時；可多段退避（10s、1m、10m）拓撲較複雜；每個延遲級別一個 queue
C. 延遲訊息外掛rabbitmq_delayed_message_exchange，送訊息時帶 x-delay任意延遲時間，單一 exchange延遲訊息存在單一節點、非高可用；大量或很長延遲不適合
D. 應用層排程失敗記錄到資料庫，排程任務重新發送可查、可控、可人工介入要自己實作，多一份狀態

實務常見組合：先用方案 A 重試 2～3 次處理瞬間錯誤（網路抖動），仍失敗就進入方案 B 的等待佇列做較長間隔的退避，最終仍失敗才進 DLQ 交給人處理。

等待佇列重試的寫法

// 等待佇列：沒有任何消費者。訊息到期後，透過預設 exchange 送回「原本的主 queue」
@Bean Queue mailRetry10s() {
    return QueueBuilder.durable("order.created.mail.retry.10s")
        .withArgument("x-message-ttl", 10_000)
        .deadLetterExchange("")                          // 空字串 = 預設 exchange
        .deadLetterRoutingKey("order.created.mail")      // = 主 queue 名稱
        .build();
}

不要把等待佇列的 DLX 指向原本的業務 exchange。若指向 order.events 並用 order.created 當 routing key，重送時會被路由到「所有」綁定 order.created 的 queue，其他本來已處理成功的消費者會再收到一次。要「只送回失敗的那個 queue」，應使用預設 exchange + queue 名稱當 routing key。

消費者端的流程：處理失敗 → 讀取 x-death 標頭（或自訂 header 如 x-retry-count）判斷已重試幾次 → 未達上限就把訊息發到對應的等待佇列並 ack 原訊息；已達上限就發到 DLQ。注意「發到等待佇列」與「ack 原訊息」之間也有失敗的可能，需用 publisher confirm 先確認再 ack。

延遲訊息與 TTL 的陷阱

單則訊息的 TTL（expiration）只在訊息到達 queue 的「頭部」時才會被檢查。如果 queue 頭部是一則 60 秒的訊息，後面排了一則 5 秒的，那 5 秒那則要等前面那則過期後才會一起被清掉。因此「用 per-message TTL + 同一個等待佇列」做不同長度的延遲會失準。要嘛每個延遲長度一個 queue（用 queue 層級的 x-message-ttl），要嘛使用延遲訊息外掛。

docker exec rabbitmq rabbitmq-plugins enable rabbitmq_delayed_message_exchange
@Bean CustomExchange delayedExchange() {
    return new CustomExchange("order.delayed", "x-delayed-message", true, false,
        Map.of("x-delayed-type", "direct"));
}
// 發送：加上 x-delay（毫秒）
rabbit.convertAndSend("order.delayed", "order.cancel", evt, m -> {
    m.getMessageProperties().setDelayLong(30L * 60 * 1000);   // 30 分鐘後才可被消費
    return m;
});

典型應用：「下單後 30 分鐘未付款自動取消」。外掛方案寫起來最短，但訊息量大或要求高可用時，改用「資料庫 + 排程掃描」或每個延遲級別一個 queue 更穩。

毒藥訊息（Poison Message）

格式錯誤、永遠無法處理的訊息，不管重試幾次都會失敗。沒有重試上限與 DLQ，它會無限循環並卡住 queue。處理原則：區分暫時性錯誤（可重試）與永久性錯誤（不要重試）。Spring 可以設定 ListenerExecutionFailedException 的不可重試例外分類（如反序列化失敗、驗證失敗直接丟 AmqpRejectAndDontRequeueException）。

練習 6-1：設計付款失敗的重試

付款通知消費者呼叫第三方 API，偶爾逾時。要求：最多重試 5 次，間隔依序 10 秒、1 分鐘、10 分鐘、1 小時、6 小時；最終進 DLQ 並告警。請描述需要的 queue 與流程。

看參考答案
  1. 主 queue payment.notify（設定 DLX 指向 payment.dlx）。
  2. 五個等待佇列：payment.notify.retry.10s / 1m / 10m / 1h / 6h，各自設定 x-message-ttl 與 deadLetterExchange=""、deadLetterRoutingKey=payment.notify。
  3. 消費者失敗時，依訊息 header 的 x-retry-count（沒有就是 0）選擇對應的等待佇列，count + 1 後重新發送；confirm 成功後 ack 原訊息。
  4. count 已達 5：發送到 DLQ payment.notify.dlq，並觸發告警。
  5. 注意消費端冪等：第三方 API 要帶 idempotency key，避免「其實上一次已成功只是回應逾時」造成重複扣款。

第 7 章常見模式與設計

1. Work Queue：把工作分給多個工人

多個消費者監聽同一個 queue，訊息輪流分派（競爭消費者）。擴充處理能力只要多開消費者。要公平分派（避免快的閒著、慢的堆積）就把 prefetch 設小（1～10）。適合耗時任務：圖片處理、報表產生、批次寄送。

2. Publish / Subscribe：一個事件，多個訂閱者

用 fanout 或 topic exchange，每個訂閱者有自己的 queue。新增訂閱者不影響既有系統。這是事件驅動架構（EDA）的基礎。

3. RPC：用訊息做請求回應

請求帶上 reply-to（回覆 queue）與 correlation-id，伺服器處理後把結果送到 reply-to，客戶端以 correlation-id 對應。RabbitMQ 提供 amq.rabbitmq.reply-to 的 direct reply-to 機制，不必為每個請求建 queue。Spring 提供 rabbit.convertSendAndReceive(...)。

RPC 通常不是好選擇。它把非同步訊息又變回同步等待：呼叫方要處理逾時、重複回應、服務端掛掉；耦合度和直接呼叫 HTTP 差不多，卻更難除錯。需要同步結果時，優先考慮 HTTP / gRPC；MQ 用在「不需要立刻拿到結果」的地方。

4. 雙寫問題與 Outbox 模式

下單時要「寫資料庫」並「發訊息」。兩個動作無法放在同一個交易內：

  • 先寫 DB 再發訊息：DB 成功、發送失敗（或程式在中間當掉）→ 訂單存在，但下游永遠沒收到。
  • 先發訊息再寫 DB：訊息發出了，DB 交易卻回滾 → 下游處理了一筆不存在的訂單。

解法是 Transactional Outbox：把「要發的訊息」當成資料，和業務資料寫進同一個資料庫交易；另一個程序負責把它發到 RabbitMQ。

CREATE TABLE outbox (
  id           BIGSERIAL PRIMARY KEY,
  event_id     UUID        NOT NULL UNIQUE,     -- 之後當作 messageId，供消費端去重
  exchange     VARCHAR(100) NOT NULL,
  routing_key  VARCHAR(200) NOT NULL,
  payload      JSONB       NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ
);
@Transactional
public Order create(CreateOrder cmd) {
    Order order = orderRepo.save(Order.from(cmd));
    outboxRepo.save(Outbox.of("order.events", "order.created", new OrderCreated(order)));  // 同一個交易
    return order;
}
@Scheduled(fixedDelay = 500)
@Transactional
public void relay() {
    // FOR UPDATE SKIP LOCKED：多個實例同時跑也不會重複撈同一批
    List<Outbox> batch = outboxRepo.lockUnpublished(100);
    for (Outbox o : batch) {
        rabbit.invoke(ops -> {
            ops.convertAndSend(o.exchange(), o.routingKey(), o.payload(), m -> {
                m.getMessageProperties().setMessageId(o.eventId().toString());
                return m;
            });
            return ops.waitForConfirms(5_000);    // 等 broker 確認才標記已發送
        });
        o.markPublished();
    }
}

Outbox 保證「資料庫有，訊息最終一定會發」，代價是可能重複發送（發成功但標記前當掉），所以消費端的冪等仍是必要的。進階做法是改用 CDC（如 Debezium）讀取資料庫日誌，不必輪詢。

5. 訊息設計的原則

原則說明
事件 vs 命令事件是「已發生的事實」（OrderCreated），發送者不在乎誰處理；命令是「請你做某事」（SendMail），有明確的接收者。優先用事件，耦合最低
必備的 metadatamessageId（去重）、correlationId（追蹤同一流程）、timestamp、type / version
Payload 大小訊息小而精。大檔案放物件儲存，訊息只放連結。只放 ID 還是放完整資料要權衡：完整資料讓消費者不必回查，但資料可能過時、增加耦合
Schema 演進只新增欄位、不刪除也不改義；消費者要忽略未知欄位（Jackson 設 FAIL_ON_UNKNOWN_PROPERTIES=false）；破壞性變更用新的 routing key 或版本號
不要放敏感資料訊息可能長期留在 DLQ、log、備份，個資與密碼別直接放進去

第 8 章叢集與高可用

叢集的基本概念

  • 多個 RabbitMQ 節點組成一個叢集，中繼資料（exchange、queue 定義、binding、使用者、vhost）會複製到所有節點。
  • 但 queue 的內容不一定複製：classic queue 只存在一個節點；quorum queue 與 stream 才會複製到多個節點。
  • 節點之間靠 Erlang 的分散式機制通訊，需要相同的 Erlang cookie，並開放 4369（epmd）與 25672（節點間通訊）等連接埠。
重要：4.0 的變化 傳統的「鏡像佇列」（classic mirrored queues）在 4.0 已經移除。舊資料與舊文章中的 ha-mode policy 不再適用，高可用請改用 quorum queue。

Quorum Queue 與多數決

每個 quorum queue 有一個 leader 與數個 follower，寫入需要多數節點確認才算成功。

叢集節點數多數可容忍掛掉幾個
110
220（比 1 個還糟：任何一台掛了就不可用）
321
532

所以叢集用奇數個節點（3 或 5）。三個節點只能容忍一個節點故障；兩個同時掛掉，quorum queue 因為失去多數而停止服務（不是遺失資料，而是等待恢復）。Leader 掛掉時，剩餘節點在幾秒內選出新 leader。

客戶端怎麼連叢集

spring:
  rabbitmq:
    addresses: rmq1:5672,rmq2:5672,rmq3:5672   # 連線失敗時依序嘗試
    username: app
    password: app-secret
  • 也可以在前面放負載平衡器（HAProxy、雲端 LB）：TCP 層轉發 5672，並設定健康檢查。
  • 客戶端要開啟自動連線恢復（Spring AMQP 預設會重連；原生 Java 客戶端需設定 automaticRecoveryEnabled），並在重連後重新宣告拓撲。
  • 叢集中的 quorum queue leader 分散在各節點，連線連到哪個節點都可以，節點間會轉送。

網路分區

叢集節點間網路斷線（partition）時，各半邊可能都認為對方掛了。cluster_partition_handling 設定處理策略，生產環境建議 pause_minority：少數派那一半自動暫停服務，等網路恢復再加入，避免「分裂腦」（兩邊各自接受寫入、資料不一致）。Quorum queue 本身以 Raft 保證一致性，天然抗分區。

不要把一個叢集跨越廣域網路（跨區域、跨機房）。RabbitMQ 叢集假設節點之間網路低延遲且穩定。跨機房的資料同步請使用 Federation（讓一個 exchange / queue 從遠端上游拉取訊息）或 Shovel（把訊息從一個 broker 的 queue 搬到另一個），而不是組成一個大叢集。

部署與升級

  • Kubernetes：使用官方的 RabbitMQ Cluster Operator，把拓撲宣告成 YAML（還有 Messaging Topology Operator 管理 queue / exchange）。
  • 磁碟使用具備足夠 IOPS 的持久儲存；quorum queue 對磁碟 fsync 效能敏感。
  • 滾動升級：一次一個節點，等它完全重新加入叢集、同步完畢，再升級下一個。升級前先看版本相容性（尤其跨大版本如 3.x → 4.x，需先升到 3.13 再升 4.x）。

流量控制與阻塞

當記憶體超過水位（vm_memory_high_watermark，預設為實體記憶體的 40%）或磁碟剩餘低於 disk_free_limit，broker 會觸發警報（alarm）並阻塞所有發布者連線：生產者的連線狀態會變成 blocked，發送動作被卡住。這是保護機制，但對線上服務就是「發送突然全部停住」，所以水位警報要在到達前就預警。

docker exec rabbitmq rabbitmq-diagnostics alarms          # 目前有無警報
docker exec rabbitmq rabbitmq-diagnostics memory_breakdown  # 記憶體都被誰佔用

安全基本功

  • 刪除或停用 guest，每個應用一個專屬使用者。
  • vhost 隔離：不同環境 / 不同業務用不同 vhost。
  • 最小權限：權限分 configure / write / read 三項，各是一個正規表示式，指定可操作的資源名稱。
  • TLS：用戶端連線與管理介面都應加密（5671、15671）。
  • 管理介面不要暴露在公網；叢集間通訊埠只在內網開放。
docker exec rabbitmq rabbitmqctl add_vhost prod
docker exec rabbitmq rabbitmqctl add_user order-svc '強密碼'
# 只允許操作 order. 開頭的資源：configure / write / read
docker exec rabbitmq rabbitmqctl set_permissions -p prod order-svc "^order\." "^order\." "^order\."
docker exec rabbitmq rabbitmqctl delete_user guest

效能調校要點

  • 連線與 channel：長連線、少連線；發布與消費分開連線；不要在多執行緒共用一個 channel。
  • 批次確認：高吞吐下，不要逐則等 confirm，改成批次發送後一起確認，或使用非同步 confirm（Spring 的 correlated 模式即是）。
  • 訊息大小：幾 KB 以內最佳；避免 MB 級訊息。
  • Queue 保持短：快速消費、短佇列效能最好；需要長期保留、重播，用 stream。
  • 多個 queue 分散負載：單一 queue 是單一 leader、單一執行緒處理，吞吐有上限。熱點流量可以分成多個 queue（Consistent Hash Exchange）。
  • 先量測再調：用 PerfTest 工具（RabbitMQ 官方壓測程式）在接近正式的硬體上測試，而不是憑感覺。

第 10 章面試題與小抄

面試題（先自己回答，再展開看重點）

1. 為什麼要用訊息佇列？有什麼代價？

好處：解耦（生產者不認識消費者）、非同步（降低回應延遲）、削峰填谷（保護下游）、可靠投遞與重試。代價：系統複雜度、最終一致性、訊息重複與亂序、除錯困難、多一個要高可用維運的元件。需要立即結果的流程不適合。

2. 說明 RabbitMQ 的訊息從發送到消費的完整路徑。

Producer 透過 channel 把訊息發給 exchange（附 routing key）→ exchange 依類型與 binding 規則路由到零個或多個 queue（無匹配則丟棄，除非 mandatory / alternate exchange）→ queue 儲存訊息 → broker 依 prefetch 派送給消費者 → 消費者處理後 ack，broker 刪除訊息；失敗則 nack，依設定放回或進入 DLX。

3. 四種 exchange 的差別？topic 的 * 與 # 呢？

direct 完全匹配；fanout 廣播忽略 key；topic 以 . 分隔單字，* 匹配剛好一個、# 匹配零或多個；headers 比對標頭。業務事件路由最常用 topic。

4. 如何保證訊息不丟？

三個環節：①生產者開 publisher confirm 與 mandatory，處理 nack / return，必要時用 Outbox；②exchange、queue durable，訊息 persistent，使用 quorum queue 並多節點；③消費者在處理成功後才 ack，不用 auto-ack，並有重試與 DLQ，避免毒藥訊息。再加上監控與告警。

5. 如何保證訊息不重複消費？

無法在傳輸層保證「剛好一次」，只能做到至少一次，所以要在消費端做冪等：天然冪等的操作、以 messageId / 業務唯一鍵在資料庫唯一索引去重、樂觀鎖條件更新，外部呼叫帶 idempotency key。

6. 如何保證訊息順序？

單一 queue + 單一消費者 + 不 requeue 才嚴格有序。多消費者並行、nack requeue、重試都會打亂順序。要「同一鍵有序、不同鍵並行」可用 Single Active Consumer 搭配多個 queue，或 Consistent Hash Exchange 依 key 分流，每個 queue 一個消費者。

7. 訊息堆積了怎麼辦？

先判斷原因：消費者掛了？變慢（下游 DB / API）？發布暴增？對策：增加消費者數與 concurrency（注意下游承受能力）、調整 prefetch、優化處理邏輯（批次、非同步）、暫時降級非核心流程、設定 TTL / 長度上限避免無限堆積、事前用監控與告警提早發現。若堆積訊息已無價值（過期的通知），可以直接清空或轉入 DLQ。

8. 什麼是死信？怎麼設計重試？

死信來源：被 reject 且不 requeue、TTL 過期、queue 滿被擠出、quorum 超過投遞次數。重試策略：Spring 內建重試處理瞬間錯誤；較長間隔用等待佇列（TTL + DLX 繞回主 queue）或延遲外掛；最終進 DLQ 告警並人工處理。要區分暫時性與永久性錯誤，永久性的不重試。

9. Classic queue 與 Quorum queue 的差別？

Classic 只存在單一節點（鏡像在 4.0 已移除）；Quorum 以 Raft 複製到多數節點，資料安全與高可用更好，是業務佇列的建議類型，代價是吞吐略低、功能有些限制（不可 exclusive、優先權有限）。Stream 則是追加式日誌，可重播。

10. prefetch 是什麼？怎麼設定？

消費者可持有的最大未確認訊息數。太小吞吐差（頻繁往返），太大負載不均、消費者當掉時重投遞量大。快速處理的任務可設 50～250，耗時任務設 1～10 以公平分派。

11. RabbitMQ 與 Kafka 怎麼選？

RabbitMQ：靈活路由、逐則確認、任務派送、低延遲、消費後刪除。Kafka：高吞吐、訊息可保留與重播、partition 內有序、適合事件溯源與資料管線。需要重播歷史、多個獨立消費群組各自讀取全量資料時選 Kafka；一般服務間的事件通知與任務佇列用 RabbitMQ。

12. 如何解決「寫資料庫」與「發訊息」的一致性問題？

Transactional Outbox：訊息與業務資料同一交易寫入 outbox 表，另一程序可靠地發送（輪詢或 CDC），發送後標記；因為可能重複發送，消費端要冪等。避免「先發訊息後寫 DB」或「寫完 DB 再發，失敗忽略」。

設計檢查清單

  1. Exchange 以領域命名，routing key 用「領域.事件」。
  2. 業務佇列使用 quorum queue、durable、有 DLX 與 DLQ。
  3. 生產者：confirm + mandatory + messageId；與資料庫的一致性用 Outbox。
  4. 消費者：auto ack、有限次數重試、永久性錯誤不重試、冪等。
  5. prefetch 與 concurrency 依任務特性調整；要保序就單消費者。
  6. 監控 Ready / Unacked / DLQ / 消費者數 / 記憶體磁碟，並有告警。
  7. 專用帳號與最小權限，刪除 guest，啟用 TLS。
  8. 叢集三節點起跳，不跨廣域網路；跨機房用 Federation / Shovel。
