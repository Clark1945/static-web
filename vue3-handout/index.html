第 0 章先看全貌：這四個東西各管什麼

Vue、Vite、Pinia、Nuxt 常被一起提起，但它們是不同層級的東西。先分清楚，後面才不會混。

名稱角色一句話
Vue 3UI 框架（核心）用響應式資料驅動畫面：資料變，畫面自動更新
Vite開發伺服器 + 建置工具開發時用瀏覽器原生 ES Module，秒開、熱更新；正式建置時打包
Vue Router官方路由網址對應到元件，SPA 必備
Pinia官方狀態管理跨元件共享狀態，取代 Vuex
Nuxt 3全端 meta-frameworkVue + Vite + Router + Nitro 伺服器 + 檔案式路由 + SSR，全部預先組好
類比 Vue 之於 Nuxt，像 React 之於 Next.js，也像 Spring Framework 之於 Spring Boot：前者是核心，後者替你做好整合與慣例。

渲染模式：為什麼需要 Nuxt

模式HTML 在哪裡產生優點缺點
CSR / SPA瀏覽器，執行 JS 後才有內容部署簡單（純靜態檔）、頁面切換順首屏慢、SEO 與社群預覽差
SSR每次請求，在伺服器上首屏快、SEO 好、資料新需要 Node 伺服器、有 hydration 的坑
SSG / Prerender建置時一次產好最快、可丟 CDN內容更新要重新建置
Hybrid（ISR / SWR）依路由混用不同頁面選最合適的快取策略要想清楚

純 Vue + Vite 專案預設是 CSR。需要 SEO、首屏效能或同時寫 API 時，就會換成 Nuxt。本講義的主線：先把 Vue 3 核心學紮實（第 2～5 章），再看狀態管理（第 6 章），最後才是 Nuxt（第 7 章）。因為 Nuxt 裡 90% 的程式碼仍然是 Vue。

最小可跑的 Vue 3 專案

npm create vue@latest my-app      # 勾選 TypeScript、Router、Pinia、Vitest、ESLint
cd my-app

第 1 章Vite：為什麼快，以及你會碰到的設定

開發與建置是兩套機制

  • 開發時：不先打包。瀏覽器請求哪個模組，Vite 就即時轉換（TS、.vue、JSX）並回傳，利用瀏覽器原生 <script type="module">。第三方套件用 esbuild 預先打包一次（pre-bundling），因為很多套件是 CJS，或由上百個小檔案組成，直接丟給瀏覽器會很慢。
  • 熱更新（HMR）：改一個檔案，只替換該模組，並保留其餘狀態。.vue 檔的 HMR 由外掛處理。
  • 正式建置：vite build 用 Rollup（新版本在逐步換成 Rolldown，用法不變）打包，做 tree-shaking、程式碼分割、雜湊檔名。
推論 開發環境和正式環境不是同一套引擎，所以偶爾會出現「dev 正常、build 後壞掉」。上線前請務必跑過 npm run build && npm run preview。

常用設定：vite.config.ts

import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
  server: {
    port: 5173,
    proxy: {
      // 開發時把 /api 轉給後端，避免 CORS
      '/api': { target: 'http://localhost:8080', changeOrigin: true },
    },
  },
  build: {
    sourcemap: true,
    rollupOptions: {
      output: {
        manualChunks: { vendor: ['vue', 'vue-router', 'pinia'] },
      },
    },
  },
})

server.proxy 只在 dev 有效。正式環境請在 Nginx / API Gateway 做反向代理，或讓後端開 CORS，這是新手最常忽略的落差。

環境變數

# 只有 VITE_ 開頭的才會暴露給前端程式碼
VITE_API_BASE=/api
VITE_APP_TITLE=My App
const base = import.meta.env.VITE_API_BASE   // 建置時被「直接替換」成字串
import.meta.env.MODE        // 'development' | 'production' | 自訂 mode
import.meta.env.DEV         // boolean
import.meta.env.BASE_URL    // vite.config 的 base

注意：前端的環境變數是在建置時寫死進 bundle，任何人都能在瀏覽器看到。API 金鑰、資料庫密碼絕對不能放 VITE_ 變數。需要機密就放在伺服器端（Nuxt 的 server routes，或你的後端）。

也因此：同一份建置結果想部署到不同環境（測試 / 正式），要嘛每個環境各建置一次，要嘛執行時才去載入一個 config.json。Nuxt 的 runtimeConfig（第 7 章）解決的正是這件事。

程式碼分割與子路徑部署

// 動態 import：Vite 會自動切成獨立的 chunk，用到時才下載
const AdminPage = () => import('@/views/AdminPage.vue')

// 部署在 https://example.com/app/ 時
// vite.config.ts → base: '/app/'

使用 history 模式的 Vue Router 時，伺服器必須把所有未知路徑回傳 index.html（Nginx 的 try_files $uri /index.html），否則重新整理深層網址會 404。

第 2 章單檔元件（SFC）與模板語法

一個 .vue 檔把一個元件的模板、邏輯、樣式放在一起。現在的標準寫法是 <script setup>：頂層宣告的變數與函式會自動暴露給模板，不用再 return。

<script setup lang="ts">
import { ref } from 'vue'

const count = ref(0)
function inc() { count.value++ }
</script>

<template>
  <button class="btn" @click="inc">點了 {{ count }} 次</button>
</template>

<style scoped>
.btn { padding: 4px 12px; }
</style>
scoped 的原理 編譯時替元素加上 data-v-xxxx 屬性，選擇器也被改寫成帶屬性的形式。想穿透到子元件內部，用 :deep(.cls)。

模板指令速查

語法用途備註
{{ expr }}文字插值只能放單一表達式，不能放陳述式（if、for）
:attr="expr"綁定屬性（v-bind）屬性名與變數同名時可寫 :id（3.4+）
@click="fn"監聽事件（v-on）修飾符 .prevent .stop .once .enter
v-if / v-else-if / v-else條件渲染真的建立 / 銷毀 DOM 與子元件
v-show切換 display元素一直存在；切換頻繁用它
v-for="item in list" :key="item.id"列表渲染key 要用穩定且唯一的值
v-model雙向綁定是 :value + @input 的語法糖；.trim .number .lazy

v-if 與 v-for 不要放在同一個元素上。Vue 3 中 v-if 優先於 v-for（Vue 2 相反），此時 v-if 取不到迴圈變數。要過濾列表，請用 computed 先算好過濾後的陣列，或把 v-if 放到外層 <template>。

class 與 style 綁定

<div :class="['card', { active: isActive, 'is-error': hasError }]"
     :style="{ color: textColor, fontSize: size + 'px' }"></div>

為什麼 key 很重要

Vue 更新列表時，用 key 判斷「哪個節點是原來那個」。沒有 key 或用 index 當 key，在列表會插入、刪除、排序時，Vue 會就地重用 DOM，造成輸入框的內容、元件內部狀態錯位到別的資料列上。

<!-- 錯：刪除第一筆後，第二筆資料會「繼承」第一筆的輸入框內容 -->
<li v-for="(todo, i) in todos" :key="i"><input v-model="draft[i]" /></li>

<!-- 對：使用資料本身的唯一 id -->
<li v-for="todo in todos" :key="todo.id">...</li>

Vue 3 相對於 Vue 2 的幾個結構性改變

  • 模板可以有多個根節點（fragment）。注意此時屬性繼承（class 等）不會自動套用，要自己用 v-bind="$attrs" 指定。
  • v-model 在元件上改為 modelValue + update:modelValue，並可多個 v-model:title。
  • 移除 $on / $off / $once、filters；.sync 併入 v-model。
  • 響應式從 Object.defineProperty 換成 Proxy（下一章）。

第 3 章響應式系統：Vue 3 的核心

原理一分鐘版

Vue 用 Proxy 包住物件。讀取屬性時，記錄「目前正在執行的 effect（渲染函式、computed、watch）依賴這個屬性」（track）；寫入屬性時，找出依賴它的 effect 重新執行（trigger）。這就是「資料變、畫面自動更新」的全部秘密。

// 極簡示意：不是 Vue 的實際原始碼
let activeEffect = null
const deps = new WeakMap()               // target → key → Set<effect>

function reactive(target) {
  return new Proxy(target, {
    get(t, key, r) { track(t, key); return Reflect.get(t, key, r) },
    set(t, key, v, r) { const ok = Reflect.set(t, key, v, r); trigger(t, key); return ok },
  })
}
function effect(fn) { activeEffect = fn; fn(); activeEffect = null }
Vue 2 的限制 Object.defineProperty 偵測不到新增屬性與陣列索引賦值，所以才有 Vue.set。Proxy 沒有這個問題。

ref 與 reactive

import { ref, reactive } from 'vue'

const count = ref(0)               // 任何型別；腳本中要用 .value
count.value++

const state = reactive({ user: { name: 'A' }, list: [] })   // 只能是物件 / 陣列
state.user.name = 'B'              // 深層響應
refreactive
適用基本型別、物件皆可只能物件 / 陣列 / Map / Set
取值腳本 .value；模板自動解包直接存取屬性
整個替換可以：x.value = newObj不行：重新賦值會斷掉響應連結
解構ref 本身可以傳遞解構後變普通值，失去響應性

實務建議：一律用 ref（Vue 官方文件也這樣建議），因為行為一致，不必煩惱型別與替換問題。reactive 留給確定不會被整個換掉的表單物件。

最常見的三個失去響應性：

const state = reactive({ count: 0 })

let { count } = state          // ① 解構：count 只是一個數字
const n = state.count          // ② 取出基本型別：同上
state = reactive({ count: 1 })  // ③ 重新賦值（const 也會報錯，用 let 則連結斷掉）

// 修正：保持引用，或用 toRefs / toRef
const { count: countRef } = toRefs(state)   // countRef 是 ref，與 state.count 連動

computed：有快取的衍生值

const price = ref(100)
const qty = ref(3)
const total = computed(() => price.value * qty.value)   // 只有依賴變動才重算

// 可寫的 computed（少用）
const full = computed({
  get: () => first.value + ' ' + last.value,
  set: (v) => { [first.value, last.value] = v.split(' ') },
})

computed 的 getter 必須是純函式：不要在裡面發 API、改別的狀態、操作 DOM。這些副作用該放在 watch 或事件處理器。

watch 與 watchEffect

// watch：明確指定來源，拿得到新舊值，預設「惰性」（不會馬上執行）
watch(keyword, (newV, oldV, onCleanup) => {
  const ctrl = new AbortController()
  onCleanup(() => ctrl.abort())            // 下一次觸發前先取消上一次請求
  fetch(`/api/search?q=${newV}`, { signal: ctrl.signal })
}, { immediate: false })

// 監聽 reactive 物件的屬性要用 getter
watch(() => state.user.name, (v) => { /* ... */ })

// 監聽多個來源
watch([a, b], ([newA, newB]) => { /* ... */ })

// watchEffect：自動收集依賴，馬上執行一次
watchEffect(() => { document.title = `${count.value} 筆` })
選項說明
immediate建立時立刻執行一次
deep深層監聽（成本高，能避免就避免）；對 reactive 物件預設就是深層
flush: 'post'等 DOM 更新後才執行回呼（需要讀取更新後的 DOM 時用）
once: true只觸發一次（3.4+）
怎麼選 要「算出一個值」→ computed。要「值變了就做某件事（發請求、寫 localStorage）」→ watch。依賴很多、不在乎舊值 → watchEffect。

更新是非同步批次的：nextTick

count.value++
console.log(el.value.textContent)   // 還是舊的！DOM 尚未更新
await nextTick()
console.log(el.value.textContent)   // 新的

同一個 tick 內多次修改狀態，只會重新渲染一次。這是 Vue 效能的基礎，也是「改了資料立刻讀 DOM 讀到舊值」的原因。

大型資料與不需深層響應的情況

  • shallowRef / shallowReactive：只追蹤第一層（.value 被替換才觸發）。適合上萬筆的大陣列、第三方實例（地圖、圖表物件）。
  • markRaw(obj)：標記此物件永遠不要被代理。
  • toRaw(proxy)：取回原始物件，常用在要結構化複製或交給第三方函式庫時。

Props 解構（3.5+）

<script setup lang="ts">
// 3.5 起，解構 props 由編譯器轉換，仍保有響應性；也可以直接寫預設值
const { title, size = 16 } = defineProps<{ title: string; size?: number }>()
// 但傳給 watch 時要包成 getter：watch(() => title, ...)
</script>

練習 3-1：防抖搜尋

寫一個 <input v-model="keyword">，使用者停止輸入 300ms 後才呼叫 search(keyword)；新輸入進來時，要取消上一次尚未完成的請求。

看參考答案 
<script setup lang="ts">
import { ref, watch } from 'vue'

const keyword = ref('')
const results = ref<string[]>([])

watch(keyword, (q, _old, onCleanup) => {
  if (!q.trim()) { results.value = []; return }
  const ctrl = new AbortController()
  const timer = setTimeout(async () => {
    try {
      const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, { signal: ctrl.signal })
      results.value = await res.json()
    } catch (e) {
      if ((e as Error).name !== 'AbortError') throw e
    }
  }, 300)
  onCleanup(() => { clearTimeout(timer); ctrl.abort() })   // 防抖 + 取消過期請求
})
</script>

重點：onCleanup 在下一次回呼觸發前（或元件卸載時）執行，一次解決 debounce 與 race condition。

第 4 章元件設計：props、事件、插槽

單向資料流

父元件透過 props 往下傳，子元件透過事件往上通知。子元件不要直接修改 props（Vue 會警告）。需要「雙向」時，用 v-model 這個約定。

<script setup lang="ts">
interface User { id: number; name: string }

const props = withDefaults(defineProps<{
  user: User
  editable?: boolean
}>(), { editable: false })

const emit = defineEmits<{
  (e: 'select', id: number): void
  (e: 'rename', id: number, name: string): void
}>()
</script>

<template>
  <div @click="emit('select', props.user.id)">
    {{ props.user.name }}
  </div>
</template>
<UserCard :user="u" editable @select="onSelect" />

defineModel：把 v-model 寫成一行（3.4+）

<script setup lang="ts">
const keyword = defineModel<string>({ default: '' })           // v-model
const page = defineModel<number>('page', { default: 1 })       // v-model:page
</script>

<template>
  <input v-model="keyword" />
</template>

<!-- 使用：<SearchBox v-model="q" v-model:page="p" /> -->

defineModel 回傳的是一個可讀寫的 ref：讀取來自父元件的 prop，寫入時自動 emit update:xxx。

插槽（slot）

<template>
  <table>
    <thead><slot name="header" /></thead>
    <tbody>
      <tr v-for="row in rows" :key="row.id">
        <!-- 作用域插槽：把資料交給使用者決定怎麼畫 -->
        <slot name="row" :row="row" :index="row.id">{{ row }}</slot>
      </tr>
    </tbody>
  </table>
</template>
<DataTable :rows="users">
  <template #header><th>姓名</th></template>
  <template #row="{ row }"><td>{{ row.name }}</td></template>
</DataTable>
設計準則 元件要「長得不同」→ 用 slot；要「行為不同」→ 用 props / 事件。一個元件開了十幾個 boolean props 時，通常該改用 slot 或拆成多個元件。

provide / inject：跨層傳遞

// 祖先
const theme = ref('dark')
provide('theme', theme)               // 傳 ref，後代才拿得到響應性

// 後代（任意層）
const theme = inject<Ref<string>>('theme', ref('light'))

適合元件庫內部（Tabs 與 TabPanel）。應用層級的共享狀態請用 Pinia，不要把 provide 當全域變數。TypeScript 下建議用 InjectionKey<T> 取代字串。

生命週期

Hook時機常見用途
onMountedDOM 已掛載操作 DOM、初始化第三方圖表、讀取 window
onUpdatedDOM 已更新很少用，優先用 watch + flush: 'post'
onBeforeUnmount / onUnmounted卸載前 / 後清除計時器、事件監聽、WebSocket
onActivated / onDeactivated被 <KeepAlive> 快取的元件進出回到頁面時重新整理資料

<script setup> 本身就相當於 Options API 的 created，所以沒有 onCreated。需要在 SSR 中只在瀏覽器端執行的邏輯，一定要放 onMounted（第 7 章）。

模板 ref（取得 DOM 或子元件）

<script setup lang="ts">
import { useTemplateRef, onMounted } from 'vue'

const input = useTemplateRef<HTMLInputElement>('input')   // 3.5+
onMounted(() => input.value?.focus())
</script>

<template><input ref="input" /></template>

子元件預設是封閉的，父元件拿不到內部變數，必須用 defineExpose({ focus }) 明確公開。這是刻意的封裝設計。

其他內建元件

  • <Teleport to="body">：把內容渲染到別處，Modal、Toast 必備。
  • <KeepAlive>：快取切換出去的元件實例，保留表單與捲動狀態。
  • <Transition> / <TransitionGroup>：進出場動畫。
  • <Suspense>：等待非同步子元件（仍標示為實驗性；Nuxt 內部有使用）。

第 5 章Composable 與 Vue Router

Composable：用函式重用「有狀態的邏輯」

Composable 是以 use 開頭、內部使用 Vue 響應式 API 的函式。它取代了 Vue 2 的 mixin，解決 mixin 的三個老問題：來源不明（this 上的東西是誰給的？）、命名衝突、隱式依賴。

import { ref, toValue, watchEffect, type MaybeRefOrGetter } from 'vue'

export function useFetch<T>(url: MaybeRefOrGetter<string>) {
  const data = ref<T | null>(null)
  const error = ref<Error | null>(null)
  const loading = ref(false)

  watchEffect(async (onCleanup) => {
    const ctrl = new AbortController()
    onCleanup(() => ctrl.abort())
    loading.value = true
    error.value = null
    try {
      const res = await fetch(toValue(url), { signal: ctrl.signal })   // url 可為 ref / getter / 字串
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      data.value = await res.json()
    } catch (e) {
      if ((e as Error).name !== 'AbortError') error.value = e as Error
    } finally {
      loading.value = false
    }
  })

  return { data, error, loading }
}
const id = ref(1)
const { data: user, loading } = useFetch<User>(() => `/api/users/${id.value}`)   // id 改變自動重抓

寫 composable 的慣例

  • 參數接受 MaybeRefOrGetter，內部用 toValue() 統一處理，呼叫端可以傳值、ref 或 getter。
  • 回傳「一個物件包著多個 ref」，使用者解構後仍保有響應性。
  • 要清理的副作用（計時器、事件）務必在 onScopeDispose / onUnmounted 清除。
  • 只在 setup 同步階段（或另一個 composable 內）呼叫，因為它依賴「目前的元件實例」。
現成的工具箱 VueUse 收錄了上百個 composable（useLocalStorage、useDebounceFn、useIntersectionObserver…），先找有沒有再自己寫。

同一個路由元件，參數變了不會重建。從 /users/1 切到 /users/2 時，Vue Router 會重用同一個元件實例，onMounted 不會再執行。要在參數變動時重新抓資料，請 watch(() => route.params.id, load, { immediate: true })，或在 <RouterView :key="route.fullPath"> 加 key 強制重建（成本較高）。

導航守衛執行順序（簡化）

  1. beforeEach全域前置
  2. beforeEnter路由設定內
  3. 元件載入解析非同步元件
  4. beforeResolve全域解析
  5. afterEach導航完成

守衛回傳 false 取消、回傳路由物件重新導向、不回傳（或 true）放行。Vue Router 4 不再需要呼叫 next()（仍相容，但容易忘記而卡住，不建議）。

第 6 章Pinia：狀態管理

什麼時候需要 store

狀態的性質放哪裡
只有一個元件用元件內的 ref
父子之間props / emit / defineModel
一組相關元件共用（Tabs）provide / inject
邏輯可重用，但每次呼叫各自獨立composable
跨頁面、全應用單例（登入者、購物車、權限、偏好設定）Pinia store
伺服器資料（列表、詳情）優先考慮 useFetch / TanStack Query 這類資料快取層，而非手動放進 store

常見的過度設計：把所有 API 回應都塞進 store，再自己處理 loading、過期、重新整理。這些伺服器狀態有專門的工具。Store 留給真正的「用戶端狀態」。

兩種寫法

import { defineStore } from 'pinia'
import { computed, ref } from 'vue'

export const useCartStore = defineStore('cart', () => {
  // state = ref；getters = computed；actions = function
  const items = ref<{ id: number; price: number; qty: number }[]>([])

  const total = computed(() => items.value.reduce((s, i) => s + i.price * i.qty, 0))

  function add(id: number, price: number) {
    const hit = items.value.find((i) => i.id === id)
    if (hit) hit.qty++
    else items.value.push({ id, price, qty: 1 })
  }

  async function checkout() {
    await fetch('/api/orders', { method: 'POST', body: JSON.stringify(items.value) })
    items.value = []
  }

  return { items, total, add, checkout }       // 沒 return 的就是私有
})
export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0 }),
  getters: { double: (s) => s.count * 2 },
  actions: { inc() { this.count++ } },
})
注意：Setup Store 的 state 一定要 return 沒有 return 的 ref 不會被當成 state，SSR 序列化、devtools 和 $patch 都看不到它。Setup Store 也沒有內建 $reset()，要自己寫。

在元件中使用

// const { items, total } = cart

// ✓ state 與 getters 用 storeToRefs；actions 可以直接解構

</script>

練習 6-1：購物車 store

在上面的 cart store 加入：remove(id)、setQty(id, qty)（qty ≤ 0 時移除該項目）、以及一個 getter count 回傳總件數。並寫 Vitest 測試涵蓋「重複加入」與「數量歸零」。

看參考答案 
function remove(id: number) {
  items.value = items.value.filter((i) => i.id !== id)
}
function setQty(id: number, qty: number) {
  if (qty <= 0) return remove(id)
  const hit = items.value.find((i) => i.id === id)
  if (hit) hit.qty = qty
}
const count = computed(() => items.value.reduce((s, i) => s + i.qty, 0))
return { items, total, count, add, remove, setQty, checkout }

// 測試
it('數量設為 0 會移除項目', () => {
  const cart = useCartStore()
  cart.add(1, 100)
  cart.setQty(1, 0)
  expect(cart.items).toHaveLength(0)
})

資料抓取：useFetch / useAsyncData / $fetch

API用途SSR 行為
useFetch(url)頁面載入時取資料（最常用）伺服器抓一次，結果放進 payload，瀏覽器 hydration 時不再重複請求
useAsyncData(key, fn)取資料的函式不是單純 URL（多個請求、第三方 SDK）同上，需要唯一的 key
$fetch(url)事件處理器中呼叫（按鈕送出）無快取、無 payload 傳遞；在 setup 頂層用會被請求兩次
const { data, status, error, refresh } = await useFetch('/api/products', {
  query: { page },                       // page 是 ref，變動時自動重新請求
  lazy: false,                           // true 時不阻塞導航，改用 status 顯示載入中
  server: true,                          // false 時只在瀏覽器端抓
  default: () => [],
})

// 按鈕送出用 $fetch
async function submit() {
  await $fetch('/api/orders', { method: 'POST', body: form })
}

常見錯誤：在 setup 頂層直接用 $fetch 取頁面資料。SSR 時伺服器跑一次，hydration 後瀏覽器又跑一次，資料抓兩次還可能造成 hydration mismatch。頁面初始資料請用 useFetch / useAsyncData。

Hydration 與 SSR 的坑

SSR 流程：伺服器渲染 HTML → 瀏覽器顯示 → 載入 JS 後 Vue「接管」既有 DOM（hydration）。若瀏覽器端首次渲染的結果和伺服器 HTML 不一致，就會出現 hydration mismatch。

造成不一致的原因解法
模板直接用 Date.now()、Math.random()、new Date() 顯示把值放進 useState 或 onMounted 後再設定
存取 window、localStorage、document（伺服器沒有）放進 onMounted，或用 if (import.meta.client) 判斷
只能在瀏覽器渲染的第三方元件（地圖、圖表）用 <ClientOnly> 包起來，或檔名加 .client.vue
HTML 結構不合法（<p> 裡放 <div>）修正標籤巢狀，瀏覽器會自動修正 DOM 造成差異
伺服器與瀏覽器時區 / 語系不同格式化時明確指定 locale 與 timeZone

跨請求狀態污染（Cross-request state pollution）。在模組頂層宣告 const user = ref(null) 並匯出，在 CSR 沒問題；但 SSR 時 Node 伺服器的模組是所有使用者共用的，A 使用者的資料可能洩漏給 B。需要 SSR 安全的共享狀態，請用 useState('key') 或 Pinia（它會為每個請求建立獨立實例）。

// ✗ 所有請求共用同一個物件
export const currentUser = ref<User | null>(null)

// ✓ 每個請求各自一份
export const useCurrentUser = () => useState<User | null>('current-user', () => null)

效能優化清單（依成本效益排序）

手法何時用
路由層級懶載入（() => import()）永遠要做，成本最低、效果最大
v-for 加正確的 key永遠要做
大型列表用虛擬捲動（vue-virtual-scroller、@tanstack/vue-virtual）數千筆以上的列表
shallowRef 存大型唯讀資料上萬筆資料、不會被深層修改

第 9 章面試題與小抄

面試題（先自己回答，再展開看重點）

1. Vue 3 的響應式怎麼運作？和 Vue 2 差在哪？

Vue 3 用 Proxy 攔截讀取與寫入：讀取時 track（記錄目前 effect 依賴這個屬性），寫入時 trigger（執行相關 effect）。Vue 2 用 Object.defineProperty 逐一屬性轉成 getter/setter，無法偵測新增 / 刪除屬性與陣列索引修改，初始化時還要遞迴遍歷整個物件。Proxy 版本是惰性的（用到才代理深層）、支援 Map / Set，效能與覆蓋度都更好。代價是不支援 IE。

2. ref 和 reactive 怎麼選？

ref 可包任何型別、可整個替換、解構傳遞不失效，但腳本要寫 .value；reactive 只接受物件，不能整體替換、解構會失去響應性。預設用 ref 保持一致，reactive 只用於固定結構的表單物件。

3. computed 和 watch 的差別？

computed 是「宣告式的衍生值」：有快取、同步、純函式、回傳值。watch 是「命令式的副作用」：資料變化時做某件事（API、儲存、操作 DOM），可非同步，拿得到新舊值。能用 computed 表達的就不要用 watch 去同步另一個 ref。

4. Vue 怎麼知道要更新哪個 DOM？Diff 與 key 的作用？

模板編譯成渲染函式，產生虛擬 DOM（vnode）；狀態變化後重新產生新 vnode，與舊的比對（diff）再更新真實 DOM。Vue 3 編譯器還做了靜態提升、patch flags（標記只有哪些屬性是動態的）與 block tree，讓 diff 只比對動態節點。key 讓列表比對能辨識同一個節點，避免就地重用造成狀態錯位。

5. 為什麼 Vue 3 偏好 Composition API？它解決了什麼？

Options API 依「選項類型」（data、methods、computed）組織程式，一個功能的程式碼會散落在各處；邏輯重用只能靠 mixin，有來源不清、命名衝突問題。Composition API 依「邏輯功能」組織，可抽成 composable 重用，TypeScript 型別推斷也自然得多。Options API 仍受支援，兩者可共存。

6. 父子元件通訊有哪些方式？各自適用？

props / emit（直接父子）、v-model / defineModel（雙向綁定約定）、provide / inject（跨層，適合元件庫內部）、模板 ref + defineExpose（父呼叫子的方法，應少用）、Pinia（全域共享狀態）、事件匯流排（Vue 3 已移除，建議用 mitt 或 store 取代）。

7. Pinia 相較 Vuex 的優勢？

沒有 mutations（只剩 state / getters / actions）；對 TypeScript 友善；天生模組化（每個 store 獨立，不必巢狀 modules 與命名空間）；支援 Composition 風格的 setup store；體積小；有 devtools、HMR、SSR 支援。Vuex 目前處於維護模式，新專案使用 Pinia。

8. 什麼是 SSR？Hydration 是什麼？為什麼會 mismatch？

SSR 是在伺服器把元件渲染成 HTML 回傳，利於 SEO 與首屏。瀏覽器載入 JS 後，Vue 不重建 DOM，而是「接管」現有 DOM、掛上事件與響應式（hydration）。若瀏覽器首次渲染結果和伺服器 HTML 不同（隨機值、時間、瀏覽器專屬 API、非法 HTML 結構），就是 mismatch，Vue 會警告甚至整個重新渲染。

9. Nuxt 的 useFetch 與 $fetch 差異？

useFetch 是對 useAsyncData + $fetch 的包裝，為 setup 階段取資料設計：SSR 時把結果放進 payload、hydration 不重發；回傳 data / status / error / refresh 響應式物件，可監聽 ref 自動重抓，並以 key 去重。$fetch 是底層的 HTTP 客戶端，用於事件處理（送出表單），在 setup 頂層使用會雙重請求。

10. 如何設計一個大型 Vue 專案的目錄與分層？

依「功能（feature）」切分比依「類型」切分更好維護：features/cart/{components, composables, store, api, types}，共用的放 shared/。API 呼叫集中在 api/ 層，不在元件中直接寫 URL；store 只放用戶端狀態；元件分展示型（只吃 props）與容器型（碰資料）；以 ESLint 規範 import 邊界、vue-tsc 與 Vitest 進 CI。
