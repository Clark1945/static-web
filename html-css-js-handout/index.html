第 0 章先看全貌：瀏覽器怎麼把檔案變成畫面

你在後端熟悉的是「請求進來、程式處理、回傳結果」。前端少了伺服器那一半：瀏覽器拿到檔案後，自己把它們變成畫面，之後還會在你的電腦上執行 JavaScript。流程大致是：

  1. 1. 解析 HTML建出 DOM 樹
  2. 2. 套用 CSS算出每個元素的樣式
  3. 3. 排版算出位置與大小
  4. 4. 繪製畫到螢幕上

JavaScript 執行時可以修改 DOM 或樣式，瀏覽器就會重做第 3、4 步。

Java 對照 瀏覽器可以想成一個會執行 JS 的 runtime，角色類似 JVM。差別是 JS 預設在單一執行緒上跑，靠事件迴圈處理等待（第 5 章）。

三種語言的分工

HTMLCSSJavaScript
負責內容與結構外觀與版面行為與互動

是程式語言嗎不是，沒有條件與迴圈不是，是規則表是

三個檔案怎麼接在一起

index.html       結構，瀏覽器先下載這個
css/style.css    外觀，由 <link> 引入
js/app.js        行為，由 <script> 引入
<link rel="stylesheet" href="css/style.css">
<script defer src="js/app.js"></script>
為什麼要 defer 沒加 defer 而 script 又放在 <head> 時，腳本執行時 DOM 還沒建好，querySelector 會回傳 null。defer 讓腳本等 HTML 解析完才依序執行。

第 1 章HTML：頁面的結構

HTML 用標籤描述內容，瀏覽器把它解析成一棵 DOM 樹。一個最小的頁面長這樣：

<!doctype html>
<html lang="zh-Hant">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>頁面標題</title>
  <link rel="stylesheet" href="css/style.css">
</head>
<body>
  <h1>標題</h1>
  <p>一段文字，裡面有<a href="https://developer.mozilla.org/zh-TW/">連結</a>。</p>
  <script defer src="js/app.js"></script>
</body>
</html>
Java 對照 Thymeleaf 或 JSP 最後吐給瀏覽器的就是這種文字。前端只是把它直接寫出來。

常用標籤

用途標籤
文字h1 到 h6、p、strong、em、code
清單ul、ol、li
連結與圖片a href、img src alt
版面語意header、nav、main、section、article、aside、footer
通用盒子div（區塊）、span（行內）
互動button、input、label、select、textarea、details
表格table、tr、th、td

區塊元素（div、p、h1）獨占一整行；行內元素（span、a、strong）跟著文字流動。

語意比外觀重要 能用 <button> 就不要用 <div onclick>。按鈕天生可用鍵盤聚焦、按 Enter 觸發，螢幕閱讀器也認得它。

屬性：id、class、data-*

<article class="event major" id="tw-1895-cession" data-year="1895">
  • id：整頁唯一，用來定位，也是網址 #id 錨點。
  • class：可以有多個、可以重複，用來套樣式與選取元素。
  • data-*：自訂資料，JS 用 el.dataset.year 讀取。
  • aria-*：給輔助科技看的狀態，例如 aria-pressed="true"。
注意 重複的 id 不會報錯，但 getElementById 只會拿到第一個，很難除錯。

表單

用 <label> 把文字和輸入框綁在一起，點文字就會聚焦輸入框。<button> 在表單裡預設是送出，不想送出就寫 type="button"。

試試看：新增一個 <li>，把 <ul> 改成 <ol>，再點一下「暱稱」兩個字。

第 2 章CSS：外觀與版面

CSS 是一張規則表，每條規則由選擇器和宣告組成：

.event {            /* 選擇器：class 含 event 的元素 */
  padding: 12px;    /* 屬性: 值; */
  border: 1px solid #ccc;
}

引入方式有三種：外部檔案（<link>，建議）、<style> 區塊、元素上的 style="..."（只適合臨時除錯）。

選擇器

寫法意思
p所有 p 標籤
.cardclass 含 card
#topid 為 top
.a .b.a 底下任何層級的 .b（後代）
.a > .b.a 的直接子層 .b
.a, .b兩者都套用
a:hover、button:focus-visible偽類：特定狀態
input[type="search"]屬性選擇器
.event::before偽元素：在元素前面生出一個內容
.event.major同時有 event 和 major 兩個 class

層疊與特異性：誰會贏

同一個屬性被多條規則命中時，特異性高的贏：行內 style，大於 #id，大於 .class、屬性、偽類，大於標籤。同等級時，寫在後面的贏。!important 能蓋過一切，但會讓之後難以維護，盡量不用。

Java 對照 有點像 Spring 的設定覆寫：application.yml 的值會被環境變數蓋掉，優先順序決定誰生效。

試試看：把 #special 那條規則刪掉，看第三行變成什麼顏色。

盒模型

每個元素都是一個盒子，由內而外是：content（內容）、padding（內距）、border（框線）、margin（外距）。預設 width 只算 content，加了 padding 和 border 會讓盒子變寬，很反直覺。所以幾乎每個專案第一條都是：

*, *::before, *::after { box-sizing: border-box; }

這樣 width 就包含 padding 與 border。

常用單位

  • px：固定像素。rem：相對根字級（預設 16px），適合字體與間距。
  • %：相對父層。vw / vh：相對視窗寬高。dvh：手機網址列伸縮時會跟著變的視窗高度。
  • fr：Grid 專用，剩餘空間的份數。

Flexbox：一維排列

把容器設成 display: flex，子元素就沿著一個方向排列。兩個最常調的屬性：justify-content 管主軸（預設水平），align-items 管交叉軸（預設垂直）。

.row {
  display: flex;
  gap: 12px;                       /* 子元素間距 */
  justify-content: space-between;  /* 主軸分配 */
  align-items: center;             /* 交叉軸對齊 */
  flex-wrap: wrap;                 /* 放不下就換行 */
}

試試看：把 justify-content 改成 center、space-between；把 align-items 改成 center、stretch；加上 flex-direction: column。

Grid：二維排列

要同時控制橫排與直排時用 Grid。歷史資料庫的時間軸就是一個 Grid：左邊一欄年份，右邊每個國家一欄。

.grid {
  display: grid;
  grid-template-columns: 96px repeat(2, minmax(0, 1fr));  /* 年份欄 + 兩個國家欄 */
  gap: 12px;
}

這個預覽很窄，用 auto-fill 加 minmax 就能不寫 media query 而自動調整欄數。試試看：把 110px 改成 60px。

position：定位

值行為
static預設，照正常流程排版
relative以自己原本的位置為基準偏移；同時是子層 absolute 的參考點
absolute脫離正常流程，相對「最近的有定位的祖先」
fixed相對視窗，捲動時不動
sticky平時正常，捲到門檻（如 top: 0）後黏住

試試看：把 .scroll 的 overflow: auto 刪掉，sticky 就失效了。

歷史網站的關鍵 sticky 只在「會捲動的容器」裡有效。所以 .scroller 要設高度並 overflow: auto，表頭與年份欄才會固定。

CSS 變數、深色模式與響應式

:root { --bg: #fff; --ink: #111; }

@media (prefers-color-scheme: dark) {
  :root { --bg: #111; --ink: #eee; }
}

body { background: var(--bg); color: var(--ink); }

/* 行動版優先：先寫手機，再往大螢幕加 */
.card { padding: 12px; }
@media (min-width: 768px) { .card { padding: 24px; } }

/* 字級在 16px 到 22px 之間隨視窗寬度縮放 */
h1 { font-size: clamp(16px, 2.5vw, 22px); }

所有顏色都放進變數，換主題或做深色模式時只要改變數。別忘了 HTML 的 <meta name="viewport">，沒有它手機會把頁面縮成桌面版。

第 3 章JavaScript 語言基礎

JS 是動態型別、單執行緒、事件驅動的語言。想試任何一行，按 F12 開瀏覽器的 Console 直接貼上就能執行。

變數與型別

const name = "Clark";   // 不會被重新指派，預設用這個
let count = 0;          // 會改變才用 let
count += 1;
// 不要用 var

typeof "a"        // "string"
typeof 42         // "number"（整數和小數都是 number）
typeof true       // "boolean"
typeof undefined  // "undefined"
typeof null       // "object"（歷史包袱）
typeof [1, 2]     // "object"（判斷陣列要用 Array.isArray）
Java 對照 const 像 final：不能重新指派，但物件內容仍然可以改。

比較與真假值

0 == "0"     // true，會偷偷轉型，別用
0 === "0"    // false，永遠用 ===

// falsy（當成 false）：false, 0, "", null, undefined, NaN
if ("") { /* 不會進來 */ }

?? 只在值是 null 或 undefined 時才用預設；|| 連 0 和空字串都會被取代。?. 讓中途遇到 null 時不報錯。

const era = event.era ?? "未分類";
const first = country?.events?.[0]?.title;
const msg = `共 ${total} 筆事件`;   // 模板字串，用反引號

函式

function add(a, b) { return a + b; }
const add2 = (a, b) => a + b;                // 箭頭函式
const greet = (name = "訪客") => `哈囉，${name}`; // 預設參數
Java 對照 箭頭函式就是 lambda。函式是一等公民，可以當參數傳、當值回傳，後面的 map、filter、事件監聽都靠這點。

物件與陣列

const e = { year: 1895, title: "馬關條約", major: true };
const { year, title } = e;            // 解構
const copy = { ...e, major: false };  // 展開：複製並覆寫

const years = [1624, 1662, 1683];
const [first, ...rest] = years;       // first = 1624, rest = [1662, 1683]

JSJava Stream用途
mapmap一對一轉換

findfilter().findFirst()找第一個符合的
some / everyanyMatch / allMatch是否有 / 是否全部

JSON

const text = JSON.stringify({ year: 1895 });  // '{"year":1895}'
const obj  = JSON.parse(text);                // { year: 1895 }

JS 物件字面量和 JSON 長得很像，但 JSON 的 key 一定要雙引號、不能有註解與結尾逗號。

檔案怎麼拆：本專案不用 ES module

現代 JS 可以用 import / export 拆檔，但 <script type="module"> 在雙擊開啟（file://）時會被瀏覽器擋下。所以歷史資料庫用一般 <script>，每支檔案包在 IIFE（立即執行函式）裡，避免變數洩漏到全域：

(function () {
  "use strict";
  const secret = 1;   // 外面看不到
})();

第 4 章DOM 與事件：讓頁面動起來

DOM 是瀏覽器把 HTML 轉成的物件樹，JS 透過全域的 document 讀寫它。

const el = document.querySelector("#stats");        // 第一個符合的元素，沒有就是 null
const cards = document.querySelectorAll(".event");  // 全部符合的

el.textContent = "共 55 筆事件";        // 當純文字寫入
el.classList.add("active");             // 增減 class
el.dataset.year;                        // 讀 data-year
el.setAttribute("aria-pressed", "true");

const li = document.createElement("li");
li.textContent = "新項目";
document.querySelector("ul").append(li);
安全 innerHTML 會把字串當 HTML 解析，字串若含使用者輸入就是 XSS 漏洞。優先用 textContent 與 createElement。

事件

button.addEventListener("click", (event) => {
  console.log("被點了", event.target);
});

常用事件：click、input（輸入框每次變動）、change、submit、keydown、scroll、hashchange。event.preventDefault() 能擋掉預設行為，例如連結跳轉或表單送出。

事件委派

不要替每個按鈕各綁一個監聽器，而是綁在父層一次，再用 event.target.closest(選擇器) 找出實際被點的元素。好處是動態新增的元素不用重新綁定。歷史資料庫的事件標題連結就是這樣處理：

grid.addEventListener("click", (ev) => {
  const a = ev.target.closest("a.anchor");
  if (!a) return;           // 點到別的地方就忽略
  ev.preventDefault();
  // ...
});

狀態 → 重繪

最容易維護的寫法是：資料放在 state，改了資料就呼叫 render() 整個重畫，不要東改一點西改一點。這正是 React 之類框架的核心想法，只是它們幫你把「重畫」做得更有效率。

試試看：把 li.textContent 那行改成 li.innerHTML = text + " "，再新增一筆內容為 <b>粗體</b> 的待辦，觀察差別。這就是 XSS 的原理。

第 5 章非同步與瀏覽器 API

JS 在單一執行緒上跑，遇到網路請求、計時器這類要等的事，會交給瀏覽器處理，完成後再把回呼排進佇列，等目前的程式跑完才輪到它。所以等待時畫面不會卡住，但「誰先執行」要特別注意。

Java 對照 沒有多執行緒與鎖的問題，但有執行順序的問題。Promise 類似 CompletableFuture，fetch 類似 HttpClient。

順序是：同步程式先全部跑完，接著 Promise 的回呼（微任務），最後才是 setTimeout（即使是 0 毫秒也要排隊）。

Promise 與 async / await

async function loadJson(url) {
  const res = await fetch(url);                       // 等網路，但不卡畫面
  if (!res.ok) throw new Error("HTTP " + res.status); // fetch 遇到 404 不會自己丟錯
  return res.json();                                  // 也是 Promise
}

async function main() {
  try {
    const data = await loadJson("/data/taiwan.json");
    console.log(data.events.length);
  } catch (err) {
    console.error("載入失敗", err);
  }
}
main();
注意 await 只能在 async 函式裡用（ES module 的最上層除外）。fetch 對 404、500 不會丟例外，要自己檢查 res.ok。

後端工程師一定會遇到：CORS 與 file://

CORS：網頁向「不同來源」（網域、埠號不同）發請求時，瀏覽器會檢查回應有沒有 Access-Control-Allow-Origin 標頭，沒有就擋下。擋的是瀏覽器，curl 和 Postman 不受影響。在 Spring Boot 用 @CrossOrigin 或 CORS 設定來放行。

file://：直接雙擊開啟 HTML 時，瀏覽器會擋 fetch 讀本機檔案。這就是歷史資料庫把資料寫在 .js 用 <script> 載入，而不是用 JSON 加 fetch 的原因。想改用 JSON，就要先用 python3 -m http.server 之類的方式開本機伺服器。

localStorage

try {
  localStorage.setItem("theme", "dark");
  const theme = localStorage.getItem("theme");   // 沒有就是 null
} catch (e) {
  // 私密模式或被停用時會丟例外，要能照常運作
}

只能存字串，物件要先 JSON.stringify。它在同網站同瀏覽器內持久，但不是安全儲存，別放密碼或 token。

第 6 章　進階篇HTML 進階：語意、表單、無障礙、資源載入

基礎篇教你「怎麼寫」。這一章回答「為什麼這樣寫才對」：瀏覽器怎麼理解你的標記、怎麼替你驗證輸入、怎麼讓只用鍵盤或螢幕閱讀器的人也能操作，以及腳本究竟什麼時候下載、什麼時候執行。

6.1　Semantic HTML：標籤是在說「這是什麼」

概念

語意標籤告訴瀏覽器、搜尋引擎和輔助科技「這塊內容是什麼」，而不只是「它長什麼樣」。div 與 span 沒有任何意義，只是容器。

標籤無障礙角色該用在
header / footerbanner / contentinfo放在頁面最外層時是全站頁首、頁尾；放在 article、section 裡就只是該區塊的頁首頁尾
navnavigation主要導覽連結群組。不必每個連結清單都包，多個 nav 要用 aria-label 區分
mainmain這頁的主要內容，每頁只有一個，讓讀屏使用者直接跳過導覽
sectionregion有主題、通常有標題的一段內容（有名稱才算 landmark）
articlearticle可以獨立存在、搬走仍然說得通：文章、貼文、留言、商品卡
asidecomplementary與主內容相關、但拿掉也不影響主旨：側欄、延伸閱讀

運作原理

瀏覽器從 DOM 另外建出一棵 無障礙樹（Accessibility Tree），每個節點有 role（是什麼）、name（叫什麼）、state（現在狀態）。螢幕閱讀器看的是這棵樹，不是畫面：它可以用快速鍵直接跳到 main、列出全部標題、列出全部連結。

div onclick 在這棵樹上的 role 是 generic，沒有名稱，也不能被聚焦；而原生 button 一出生就帶著：role=button、可 Tab 聚焦、Enter 與空白鍵觸發、disabled 狀態、表單 submit 行為。用 div 重做，這些你都得自己補齊，而且大概會漏。

<a href><button>
做什麼前往另一個位置（URL）在目前頁面執行動作
右鍵 / 新分頁 / 複製連結可以不行
鍵盤EnterEnter + Space
在 form 內無作用預設是 submit

判斷法：改變的是「網址」用 a，改變的是「畫面或資料」用 button。<a href="#" onclick="..."> 兩邊都做不好。

標題 h1–h6 是文件大綱，不是字級。一頁一個 h1，不要為了字比較小而從 h2 跳到 h4，字級交給 CSS。section 與 article 的判斷：「把它整塊搬到別的頁面或 RSS 還說得通嗎？」說得通是 article；它只是本頁一段有主題的內容就是 section；只是為了套樣式，用 div。

常見錯誤：div 湯

<div class="header">
  <div class="logo">Shop</div>
  <div class="menu">
    <div onclick="go('/products')">商品</div>
    <div onclick="go('/cart')">購物車</div>
  </div>
</div>
<div class="content">
  <div class="title">本週新品</div>
  <div class="card">
    <div class="title">無線耳機</div>
    <div class="buy" onclick="addToCart(1)">加入購物車</div>
  </div>
</div>

讀屏軟體看到的只有一堆「群組」：沒有頁首、沒有導覽、沒有標題可以跳；選單項目不能用 Tab 抵達，也不能在新分頁開啟；「加入購物車」鍵盤根本按不到。

正確做法

<header>
  <a href="/" class="logo">Shop</a>
  <nav aria-label="主選單">
    <ul>
      <li><a href="/products">商品</a></li>
      <li><a href="/cart">購物車</a></li>
    </ul>
  </nav>
</header>
<main>
  <h1>本週新品</h1>
  <article>
    <h2>無線耳機</h2>
    <button type="button" onclick="addToCart(1)">加入購物車</button>
  </article>
</main>

導覽用 a（可在新分頁開啟、可複製連結），動作用 button，內容有標題層級，頁面有 landmark。樣式完全不受影響，因為外觀本來就該交給 CSS。

實際應用

  • 自動化測試：Playwright、Testing Library 用 getByRole('button', { name: '加入購物車' }) 找元素。語意正確，測試就不用綁 class 名稱，也不會因為改版而壞。
  • SEO 與分享預覽：爬蟲靠標題層級與 main/article 判斷主要內容。
Vue / Nuxt 對照

<NuxtLink> 與 <RouterLink> 渲染出來的是真正的 <a href>，所以站內導覽請用它們，不要用 @click="router.push(...)" 掛在 div 上。元件裡的 <slot> 也要想好外層是 article 還是 li，語意是元件契約的一部分。

6.2　表單與驗證：把規則交給瀏覽器

概念

瀏覽器內建一套「約束驗證（Constraint Validation）」：你在標籤上宣告規則，瀏覽器就會在送出前檢查、擋下、顯示訊息，不需要任何 JavaScript。JS 只在需要客製時才介入。

屬性效果與注意事項
required不可空白
type="email|url|number|date"格式檢查，同時決定手機鍵盤與數值解析。電話、郵遞區號、身分證字號不是「數字」（前導 0 會消失），用 type="text" inputmode="numeric"
pattern正規表達式，必須整串符合（隱含 ^(?:…)$）。只對文字類 input 有效；建議加 title 說明規則
min / max / stepnumber、date、range 的範圍與間隔
minlength / maxlength字數。minlength 只在使用者編輯過之後才檢查，程式設定的預設值不會觸發

運作原理

  1. 送出流程：使用者按送出或 Enter，瀏覽器逐一檢查控制項。只要有一個無效，就對它觸發 invalid 事件、跳出氣泡，而且不會觸發 submit 事件。全部有效才會進到你的 submit handler。
  2. API：每個控制項有 validity（valueMissing、typeMismatch、patternMismatch、tooShort、rangeUnderflow、customError …）與 validationMessage。checkValidity() 只回傳布林值（會觸發 invalid）；reportValidity() 還會顯示氣泡；setCustomValidity(msg) 設定自訂錯誤，傳空字串才會清除。
  3. 樣式：:invalid 在使用者還沒碰之前就生效（一打開頁面全是紅框）。改用 :user-invalid，它在使用者互動之後才套用。
  4. FormData：new FormData(form) 收集所有「有 name、沒有 disabled、已勾選」的控制項。同名欄位（checkbox 群組）要用 getAll()；Object.fromEntries(fd) 會讓後者蓋掉前者。直接 fetch(url, { method: 'POST', body: fd }) 會以 multipart 送出，不要自己設 Content-Type，否則 boundary 會遺失。
  5. 前端驗證 vs 後端驗證：前端驗證是為了體驗（即時回饋、少一次往返）；後端驗證才是安全邊界，因為任何人都能用 curl 繞過前端。兩邊都要做。Spring Boot 用 @Valid 加 Bean Validation（@NotBlank、@Email、@Size），回 400 與欄位錯誤；前端把這些錯誤對應回欄位。兩處的規則會不同步，以後端為準。
  6. 避免重複提交：在 submit 事件裡停用送出鈕並用旗標擋住（Enter 與按鈕走同一條路）；後端也要冪等（idempotency key 或唯一鍵），因為使用者還能重新整理、連點、網路重試。

試試看：什麼都不填就按送出，看 Console 輸出的 invalid 原因；把 type="number" 的 min 改掉；把 invalid 的 capture 參數 true 拿掉，看看為什麼收不到事件。

常見錯誤

<form>
  <input id="email" placeholder="Email">
  <input id="age" placeholder="年齡">
  <button type="button" onclick="submitForm()">送出</button>
</form>
<script>
function submitForm() {
  const email = document.getElementById("email").value;
  if (!email.includes("@")) { alert("Email 格式錯誤"); return; }   // 自己重寫了一次驗證
  const age = Number(document.getElementById("age").value);            // 空字串會變成 0
  api.post("/signup", { email, age });
}
</script>

三個問題：按鈕是 type="button"，欄位多於一個時 Enter 根本送不出去，鍵盤使用者被擋在門外；自己寫的檢查繞過了瀏覽器已經提供的驗證與錯誤氣泡，而且規則會和 HTML 屬性互相矛盾；Number("") 是 0，空白被悄悄當成合法值。

正確做法

規則寫在屬性上，監聽 submit 而不是按鈕的 click，如上方「試試看」所示。伺服器回傳欄位錯誤時，用 setCustomValidity 對應回欄位，並記得在使用者再次輸入時清掉：

const res = await fetch("/api/signup", { method: "POST", body: new FormData(form) });
if (res.status === 400) {
  const { errors } = await res.json();             // 例如 { email: "此 Email 已註冊" }
  for (const [name, message] of Object.entries(errors)) {
    const input = form.elements[name];
    input.setCustomValidity(message);
    input.addEventListener("input", () => input.setCustomValidity(""), { once: true });  // 不清掉就永遠無效
  }
  form.reportValidity();                           // 顯示第一個錯誤氣泡
}

實際應用

  • 註冊、結帳、後台 CRUD 的表單，大部分規則（必填、格式、長度）用屬性就夠，複雜的跨欄位規則（確認密碼、起訖日期）才用 setCustomValidity。
  • 送出前用 form.requestSubmit() 取代 form.submit()：前者會跑驗證並觸發 submit 事件，後者兩者都略過。
Vue / Nuxt 對照

用 <form @submit.prevent="onSubmit">，不要在按鈕上掛 @click，才能保留原生驗證與 Enter 送出。.prevent 修飾符等於 e.preventDefault()。表單函式庫做的，大多是在這套原生機制之外多管一層規則與狀態。

小測驗

表單有 required 欄位是空的，使用者按下送出。submit 事件會怎樣？

練習 6.2：確認密碼

完成 syncValidity()：兩次密碼不同時，讓第二個欄位變成「無效」並帶有訊息；相同時要清掉。

提示與參考答案

提示：setCustomValidity(訊息) 設定錯誤，setCustomValidity("") 清除。兩個欄位的 input 事件都要呼叫同一個函式。

解析：忘記傳空字串清除，是 setCustomValidity 最常見的 bug，欄位會永遠停在無效狀態。

6.3　無障礙：鍵盤、焦點與 ARIA

概念

無障礙讓這些人都能用你的頁面：螢幕閱讀器使用者、只用鍵盤的人、低視力者，以及暫時受限的人（單手拿東西、強光下）。對工程師還有附帶好處：語意與鍵盤做對了，自動化測試與 SEO 也跟著變好。

ARIA 第一規則

能用原生元素就不要用 ARIA。ARIA 只改「無障礙樹」，不會加上任何行為：role="button" 不會讓 div 能被聚焦，也不會讓它回應 Enter。原生 button、dialog、details、label 已經內建這些。

運作原理

名稱怎麼來（簡化後的優先順序）：aria-labelledby → aria-label → 原生來源（label、alt、按鈕內文、legend）→ title。aria-labelledby 指向頁面上已存在的可見文字；aria-label 用在沒有可見文字的控制項，例如只有圖示的按鈕。

屬性用途
aria-expanded放在「觸發按鈕」上，表示它控制的區塊現在是展開還是收合
aria-controls指向被控制區塊的 id（輔助用，支援度不一，不能只靠它）
aria-live / role="alert"區域內容改變時朗讀。區域必須先存在於 DOM，之後再改內容才會被播報
aria-invalid + aria-describedby標記錯誤欄位，並連到錯誤訊息
aria-hidden="true"從無障礙樹移除。不要用在可聚焦元素上
tabindex0 加入 Tab 順序（自訂元件）；-1 只能用 focus() 聚焦（例如錯誤摘要）；正數絕對不要用，它會打亂整頁的順序

鍵盤與焦點：Tab 順序等於 DOM 順序，所以用 CSS 把視覺順序重排（order、Grid）會讓焦點跳來跳去。:focus-visible 的樣式不能拿掉：outline: none 是最常見的無障礙 bug。

Modal 的四條規則：開啟時焦點移進去；Tab 不能跑到背景（focus trap）；Esc 可關閉；關閉後焦點回到觸發它的按鈕。原生 <dialog>.showModal() 全部自動處理（背景變 inert、Esc、焦點歸還），所以優先用它。

為什麼有些網頁只能用滑鼠？常見原因：click 掛在 div/span 上所以不能聚焦；選單只用 :hover 展開；outline 被移除所以看不到焦點；自製下拉選單沒處理方向鍵；Modal 沒有 focus trap，關掉後焦點掉回頁面最上方；拖曳是唯一的操作方式。

這是 disclosure 模式，適合網站導覽與下拉內容。不要因為叫做「選單」就套 role="menu"：那是桌面應用程式式的選單，使用者會期待完整的方向鍵操作，做不到反而更糟。

試試看：開啟後按 Tab，焦點不會跑到背景；按 Esc 關閉，焦點自動回到「刪除帳號」按鈕。<form method="dialog"> 的按鈕會關閉 dialog，並把它的 value 放進 returnValue。把破壞性操作的預設焦點放在「取消」，是刻意的設計。

好的錯誤提示有四件事：文字說明（不只靠紅色）、aria-describedby 把訊息連到欄位、aria-invalid 標記狀態、把焦點帶到第一個錯誤。role="alert" 的區域在頁面載入時就存在，之後只改文字，才會被朗讀。

常見錯誤

<div class="btn" role="button" onclick="save()">儲存</div>     <!-- role 只改名稱，沒有給它聚焦與 Enter -->
<style>button:focus { outline: none }</style>                  <!-- 鍵盤使用者看不到焦點 -->
<div aria-label="關閉" onclick="closeDialog()">×</div>              <!-- generic 元素上的 aria-label 常被忽略 -->
<button aria-label="儲存">儲存</button>             <!-- 多餘；可見文字改了還會不同步 -->

正確做法

<button type="button" onclick="save()">儲存</button>
<style>button:focus-visible { outline: 3px solid #1f5fbf; outline-offset: 2px }</style>
<button type="button" aria-label="關閉">×</button>      <!-- 沒有可見文字，才需要 aria-label -->

實際應用

  • 每次合併前做 30 秒鍵盤測試：滑鼠放一邊，只用 Tab、Shift+Tab、Enter、Space、Esc 走完主要流程。Lighthouse 與 axe 只能抓出一部分問題，抓不到「焦點順序合不合理」。
  • 自己做複雜元件（combobox、tabs、日期選擇器）很難做對，多半直接採用 Headless UI、Reka UI 這類 headless 元件庫：它們的價值就是替你處理鍵盤與 ARIA 細節。
Vue / Nuxt 對照

Vue 的 :aria-expanded="open" 會把布林值轉成字串，注意是 "true"/"false"。Modal 如果用 <Teleport to="body"> 傳送到 body（為了避開 z-index 問題，見 7.1），要自己確認焦點管理沒有因為 DOM 位置改變而失效。

第 7 章　進階篇CSS 進階：疊層、Flexbox、Grid、響應式

基礎篇的 CSS 讓你「把東西排出來」。這一章解決的是排出來之後的怪事：z-index: 9999 卻被蓋住、文字不肯截斷、卡片網格在手機上爆開。每一個都有明確的規則可循，不是玄學。

7.1　Stacking Context：為什麼 z-index: 9999 沒用

概念

z-index 不是全域的數字大賽。它只在同一個層疊上下文（stacking context）裡比較。每個層疊上下文是一個封閉的小宇宙：裡面的元素不管 z-index 多大，整體都被當成「父層疊上下文裡的一個元素」去和別人比。

運作原理

以下任一條件會讓元素建立新的層疊上下文（常見的）：

  • 根元素 html
  • position: relative/absolute 且 z-index 不是 auto；position: fixed/sticky（永遠建立）
  • flex / grid 的子項目且 z-index 不是 auto（不需要 position）
  • opacity < 1、transform、filter、perspective、clip-path、mask
  • isolation: isolate、mix-blend-mode（非 normal）、will-change 指定上述屬性、contain: layout/paint

在同一個層疊上下文內，由下到上的繪製順序大致是：背景 → 負 z-index 子項 → 一般流內元素 → 浮動 → 行內內容 → z-index: 0/auto 的定位元素 → 正 z-index（由小到大）。同 z-index 時，DOM 較後面的蓋住前面的。

下面的 bug：為什麼 tooltip（9999）輸給 content（2）

  • root stacking context
    • .sidebar z-index: 1 → 新的上下文
      • .tip z-index: 9999 （只在 sidebar 內比大小）
    • .main z-index: 2 → 新的上下文

在 root 這一層比較的是 sidebar(1) 與 main(2)；tip 的 9999 被關在 sidebar 裡面，與 main 無關。

試試看：刪掉 .sidebar 的 z-index: 1，重新執行。tooltip 浮上來了，因為 sidebar 不再是上下文，tip 直接參與 root 的比較。

常見錯誤

.card:hover { transform: translateY(-2px); }      /* 無意間讓每張卡片變成新的上下文 */
.dropdown   { z-index: 99999; }                   /* 在 .card 裡面 → 被下一張卡片蓋住 */
.modal      { z-index: 2147483647; }              /* 軍備競賽：治標不治本 */

正確做法

  • 找出元兇：從被蓋住的元素往上走，找第一個建立上下文的祖先（Chrome DevTools → Elements 選取元素 → 在 Layers／Computed 面板檢查 transform、opacity、z-index、position；或用 getComputedStyle 逐層檢查）。
  • 移除不必要的上下文，或把 z-index 建立在同一層。
  • 主動隔離：給元件根節點 isolation: isolate，讓它內部的 z-index 不外洩，也不受外部影響（比靠運氣好）。
  • 讓覆蓋層脫離元件：Modal、Dropdown、Toast 掛到 body 底下，或用原生 <dialog> / Popover API（它們在 top layer，不受任何上下文影響）。
  • 用 CSS 變數建立一套 z-index 分層表（--z-dropdown、--z-modal）。
Vue / Nuxt 對照

<Teleport to="body"> 就是把元件的 DOM 搬到 body 底下，正是為了逃出這種疊層囚籠。UI 庫的 Dialog、Select 選項面板多半內建 Teleport；自己寫的覆蓋層遇到「被蓋住」時，第一個懷疑對象是祖先的 transform 或 overflow。

小測驗

.a{position:relative;z-index:1} 裡有 .x{position:absolute;z-index:999}，旁邊有 .b{position:relative;z-index:5}。.x 與 .b 重疊時誰在上面？

練習 7.1：不改 tooltip，讓它浮到最上面

修改 CSS，讓 tooltip 與 main 重疊的位置，最上層是 tooltip；tooltip 要保持在 sidebar 內（不能搬動 HTML）。

提示與參考答案

提示：問題不在 tip 的數字，而在 sidebar 這一層。你有兩條路：讓 sidebar 不成為上下文，或讓整個 sidebar 贏過 main。

解析：這裡把 sidebar 提到 3，比 main 的 2 大，整個 sidebar（含 tip）就在 main 之上。另一個解法是移除 sidebar 的 z-index，讓 tip 的 9999 直接在 root 比較。

7.2　Flexbox 深入：空間是怎麼分配的

概念

Flexbox 是一維排版：沿主軸分配剩餘（或不足）的空間。基礎篇你學過 justify-content 與 align-items。真正決定每個項目多寬的是這三個屬性：

意義預設
flex-basis分配空間前的「起始大小」；auto 表示看 width/內容auto
flex-grow有剩餘空間時，按比例瓜分0
flex-shrink空間不足時，按「比例 × 基準大小」縮小1

運作原理

  1. 先把每個項目放上 flex-basis，算出總和與容器寬度的差。
  2. 有剩餘：按 flex-grow 比例加上去。不足：按 flex-shrink × basis 比例扣掉。
  3. 每個項目被 min-width／max-width 夾住，被夾住的項目退出，剩下的重算。
最容易踩的雷：min-width: auto

flex 項目的 min-width 預設是 auto，意思是「不能小於內容的最小寬度」。長字串、長網址、nowrap 的文字，內容最小寬度就是整行。所以它「縮不下去」，把容器撐爆。注意兩個細節：(1) 項目自己若設了 overflow（非 visible），auto 會變成 0，所以問題通常出在外面那一層沒設 overflow 的 flex 項目，裡面的省略號子元素不會救它；(2) 解法是在那個 flex 項目上寫 min-width: 0（縱向 flex 對應 min-height: 0，是可捲動區塊的標準寫法）。

flex: 1 是縮寫，展開為 flex: 1 1 0% （grow 1、shrink 1、basis 0）。basis 為 0 代表所有人從 0 開始平分，所以 flex:1 的多個項目會等寬；而 flex: auto（1 1 auto）是從內容寬度開始分，結果不等寬。

常見錯誤

.list-item { display: flex; gap: 8px; }
.list-item .body { flex: 1; }                       /* 外層 flex 項目：沒有 min-width:0 */
.list-item .name { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
/* .body 的最小寬度 = .name 的完整文字寬度 → 長檔名把整列撐出畫面，省略號永遠不出現 */

正確做法：後台典型的三欄版面

.admin { display: flex; min-height: 100vh; }
.sidebar { flex: 0 0 240px; }                      /* 固定寬，不長不縮 */
.content { flex: 1; min-width: 0; }                /* 吃掉剩餘寬度，且允許內部（表格、長文字）縮小 */
.content .table-wrap { overflow-x: auto; }         /* 寬表格在自己的框內捲動，不撐破頁面 */
.list-item .body { flex: 1; min-width: 0; }         /* 讓 .body 可以縮到比內容還窄 */
.list-item .name { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }

實際應用

  • Sticky 頁首 + 可捲動內容：外層 display:flex; flex-direction:column; height:100vh，內容區 flex:1; min-height:0; overflow:auto。
  • Tailwind 的 flex-1 就是 flex: 1 1 0%，truncate 要搭 min-w-0 才會在 flex 子項生效。

小測驗

容器 300px，三個子項目都是 flex: 1，內容長短不一。各自寬度？

練習 7.2：讓長檔名顯示省略號

只改 CSS，讓整列不超出 320px，且檔名被省略號截斷。

提示與參考答案

提示：想想外層 flex 項目 .body 的 min-width 預設值。

7.3　Grid 深入：二維排版與自動換行

概念

Grid 同時控制列與欄。選擇原則：內容決定大小、排成一排就好 → Flexbox；版面（格線）決定大小、需要對齊欄位 → Grid。兩者可以混用：外層頁面用 Grid，元件內部用 Flex。

運作原理

  • fr：剩餘空間的份數。1fr 2fr 是 1:2。注意 1fr 其實是 minmax(auto, 1fr)，最小值是內容寬度，所以長內容會撐破；用 minmax(0, 1fr) 修正（和 flex 的 min-width: 0 同一個道理）。
  • repeat(3, 1fr) 固定三欄；repeat(auto-fill, minmax(200px, 1fr)) 則是「容器放得下幾欄就幾欄，每欄至少 200px」，不需要 media query。
  • auto-fill vs auto-fit：項目少於可容納欄數時才看得出差別。auto-fill 保留空的欄位（項目維持 200px 左右不會被拉大）；auto-fit 把空欄位收成 0，現有項目被拉伸填滿整列。
  • gap 取代 margin hack；justify-items / align-items 對齊「格子內的項目」；justify-content / align-content 對齊「整組格線」在容器內的位置（容器比格線大時才有用）。

用上方的寬度按鈕切換預覽寬度（會自動重新執行），看輸出的項目寬度。寬度夠大時，auto-fill 的三個格子停在原本的欄寬（空欄被保留），auto-fit 則平分整列。

常見錯誤

.cards { display: grid; grid-template-columns: repeat(3, 1fr); gap: 16px; }
@media (max-width: 900px) { .cards { grid-template-columns: repeat(2, 1fr); } }
@media (max-width: 560px) { .cards { grid-template-columns: 1fr; } }
/* 三段 media query，斷點寫死；放進較窄的側欄裡（不是整頁變窄）仍然是 3 欄 */

正確做法：不用 media query 的卡片網格

.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(min(240px, 100%), 1fr));
  gap: 16px;
}
/* min(240px, 100%): 容器比 240px 還窄時（手機）不溢出 */

實際應用

  • 商品／文章卡片列表、圖庫：auto-fill + minmax 一行解決。
  • 後台版面：grid-template-columns: 240px minmax(0, 1fr)，側欄固定、主區可縮；需要頁首與頁尾時用 grid-template-areas。
  • 表單：兩欄標籤／輸入框對齊，用 grid-template-columns: max-content 1fr。

小測驗

容器可放 5 欄，但只有 2 個項目。哪個關鍵字會讓這 2 個項目被拉寬填滿整列？

練習 7.3：不用 media query 的自適應網格

目前永遠是 4 欄，在窄螢幕會擠成一團。請只改 .cards 的 grid-template-columns，使 300px 寬時為 1 欄、700px 寬時至少 3 欄，且不溢出。

提示與參考答案

提示：repeat(auto-fill, minmax(?, 1fr))。「?」要小於 300 才能在 300px 寬時是一欄，也要夠大讓 700px 不會變成 6 欄以上也沒關係，只要至少 3 欄。

解析：200px 的最小欄寬在 300px 容器放得下 1 欄（含 gap 放不下 2 欄），700px 可放 3 欄。

7.4　響應式設計：選對策略

概念

響應式不是「寫三組 CSS」。更好的順序是：先讓版面本身有彈性（Flex/Grid、clamp、min），斷點只處理「結構真的要改」的地方，例如側欄收進抽屜。

工具依據適合
@media (min-width: 768px)視窗（viewport）整頁結構：導覽列、側欄的出現與否
@container (min-width: 400px)最近的 container 祖先寬度可重複使用的元件（同一張卡片放在主區或側欄會不同）
clamp(min, ideal, max)視窗或容器單位連續變化的字級、間距，不需要斷點
Grid auto-fill/minmax容器寬度項目數量自動換行

運作原理

  • Mobile-first：預設樣式寫給手機，用 min-width 往上加。好處是手機載入的規則最少，且「往大加東西」比「往小還原東西」容易推理。
  • <meta name="viewport" content="width=device-width, initial-scale=1">：沒有它，手機會用約 980px 的假寬度渲染，所有 media query 都「失靈」。
  • clamp(1rem, 0.8rem + 1vw, 1.5rem)：最小 1rem、最大 1.5rem，中間隨視窗平滑變化。用 rem 組合 vw，才會尊重使用者的字級設定。
  • Container queries：先在父層宣告 container-type: inline-size，子孫才能用 @container。注意容器不能依賴自己的內容寬度來決定寬度。

切換預覽寬度：同一個 .card，在寬的主區是兩欄、在窄的側欄永遠是一欄，與整頁寬度無關。這是 media query 做不到的。

常見錯誤

/* 1. 缺 viewport meta */
/* 2. 字級用 px 加 vw：放大瀏覽器字級無效 */
h1 { font-size: calc(12px + 2vw); }
/* 3. 把元件的版型綁在視窗上 */
@media (min-width: 768px) { .card { grid-template-columns: 120px 1fr; } }  /* 放在窄側欄也會變兩欄，被擠扁 */
/* 4. 斷點用裝置名稱思考（iPad、iPhone） */

正確做法與策略選擇

  • 後台儀表板：Grid 版面 240px minmax(0,1fr)；小螢幕時用 media query 把側欄改成抽屜（結構改變 → viewport）；統計卡片用 auto-fill/minmax。
  • 卡片列表：容器層級用 auto-fill/minmax 決定欄數；單張卡片內部用 container query 決定圖文排列。
  • 可適應的側欄：grid-template-columns: minmax(200px, 20%) minmax(0, 1fr)，或 clamp(200px, 20vw, 280px) 1fr。
  • 斷點依「內容開始壞掉的寬度」決定，不依裝置型號。
Vue / Nuxt 對照

想在 JS 裡依寬度切換元件時，用 matchMedia（或 VueUse 的 useMediaQuery）而不是監聽 resize；純樣式的差異盡量留在 CSS，避免 SSR 與客戶端第一次渲染結果不一致（hydration mismatch）。

小測驗

同一張商品卡會被放在主內容區（寬）和側欄（窄）。要讓它依自己所處空間切換圖文排列，該用什麼？

練習 7.4：mobile-first 的後台版面

預設（手機）：側欄在上方、內容在下方（單欄）。視窗 ≥ 700px：左側欄固定 160px，右側內容填滿。補上缺的規則（只用 min-width media query）。

提示與參考答案

提示：預設什麼都不用寫（block 本來就上下排）；寬螢幕才需要 display: grid 與欄寬。檢查會依預覽寬度判斷，用預覽列的寬度按鈕兩種都試一次。

第 8 章　進階篇JS 核心機制：作用域、參考、this、原型

Java 背景的人學 JavaScript，最容易卡關的四個地方：變數住在哪（作用域與閉包）、賦值到底複製了什麼（值與參考）、this 指向誰、以及「class 其實不是 class」。每一節都附上與 Java 對照。

8.1　作用域與閉包

概念

作用域決定一個名稱在哪些程式碼裡可見。JS 採詞法作用域（lexical scope）：可見範圍由「程式碼寫在哪裡」決定，不是由「在哪裡被呼叫」決定。閉包是函式加上它被建立時所在的作用域：函式離開原本的位置後，仍然能讀寫那些外層變數。

運作原理

  • 每次進入函式或區塊，引擎建立一個環境（Environment Record），其中有名稱與值，以及指向外層環境的連結。查找變數時沿著這條鏈往外找，找不到就是 ReferenceError。
  • var：函式作用域，會提升（hoisting）且初始化為 undefined；let / const：區塊作用域，提升後處於暫時性死區（TDZ），宣告之前存取會丟 ReferenceError。const 只是不能重新賦值，物件內容仍可變。
  • 閉包保存的是變數本身（參考），不是建立當下的值。所以多個函式可以共用同一份狀態；而 for (let i…) 之所以安全，是因為每一圈都有自己的新 i。
  • 與 Java 對照：Java 的 lambda 只能捕捉 effectively final 的區域變數（值的拷貝）；JS 的閉包能改寫被捕捉的變數。要在 Java 做同樣的事要用 AtomicInteger 或欄位。

常見錯誤

// 1. 迴圈裡用 var + 非同步
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);   // 3 3 3

// 2. 閉包抓住大物件，造成記憶體一直不被釋放
function attach(el) {
  const hugeData = loadHugeData();
  el.addEventListener("click", () => console.log(hugeData.length));  // 只要 listener 還在，hugeData 就在
}

正確做法

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);   // 0 1 2

function attach(el) {
  const length = loadHugeData().length;                // 只留需要的
  el.addEventListener("click", () => console.log(length), { once: true });
}

實際應用

  • 私有狀態與工廠函式、once(fn)、記憶化（memoize）、debounce／throttle（見 10.2）都是閉包。
  • React 的 Hook 與 Vue 的 setup()、composables 全部建立在閉包上：setup 只執行一次，裡面宣告的函式靠閉包持續存取同一份 ref。
Vue / Nuxt 對照

在 watch 或事件 handler 裡讀到「舊值」，通常是閉包抓到了某次渲染／某次解構出來的值：const { count } = reactive(state) 解構後 count 只是數字，已經和 state 脫鉤。請用 toRefs 或直接用 state.count。

小測驗

const fs=[]; for (var i=0;i<3;i++) fs.push(()=>i); console.log(fs.map(f=>f())) 輸出什麼？

練習 8.1：寫一個 once(fn)

實作 once(fn)：回傳一個新函式，第一次呼叫時執行 fn 並記住結果，之後不論傳什麼參數都直接回傳第一次的結果，fn 不會再被呼叫。

提示與參考答案

提示：需要兩個外層變數：「是否已執行」和「結果」。不能用「結果是否為 undefined」來判斷是否執行過，原因見最後一條檢查。

8.2　值與參考：複製了什麼

概念

原始型別（number、string、boolean、null、undefined、symbol、bigint）賦值時複製值。物件（包含陣列、函式、Date、Map）賦值時複製參考：兩個變數指向同一個物件。JS 的函式參數一律是「傳值」，但物件變數的「值」就是參考，這與 Java 傳物件參考的行為相同。

運作原理

做法複製深度注意
{...obj} / [...arr] / Object.assign淺層：只複製第一層巢狀物件仍共用
structuredClone(x)深層支援 Date、Map、Set、循環參考；不能複製函式、DOM 節點，也不能複製 Vue 的 Proxy（丟 DataCloneError）；class 實例會失去原型
JSON.parse(JSON.stringify(x))深層（有損）Date 變字串、undefined／函式消失、NaN 變 null、循環參考丟錯

另外三個常見坑：=== 對物件比較的是參考，{} === {} 是 false；const 凍結的是綁定，不是內容；Object.freeze 只凍第一層。

Vue 的 reactive 與 ref 怎麼處理參考

  • reactive(obj) 回傳 obj 的 Proxy，不是副本；改 proxy 會改到原物件，同時觸發更新。把 reactive 物件整個換掉（state = {...}）會失去反應性，要改欄位或用 Object.assign(state, next)。
  • ref(x) 把值包進 { value }，因為原始值沒辦法被「參考」。模板會自動解包，script 裡要寫 .value。
  • 需要「某一刻的快照」（送 API、存草稿、structuredClone）時，用 toRaw(state) 取回原物件再複製，或 structuredClone(toRaw(state))。
  • Pinia 的 store 也是 reactive，const { name } = store 一樣會斷線，請用 storeToRefs。

常見錯誤

// Pinia / reactive: 「複製一份來編輯」，結果直接改到 store

8.3　this、箭頭函式、call / apply / bind

概念

Java 的 this 永遠是當前物件。JS 的 this 是呼叫時決定的（箭頭函式例外）：同一個函式，換個呼叫方式，this 就不同。

運作原理：判斷規則（優先順序由高到低）

  1. new Foo()：this 是新建立的物件。
  2. fn.call(obj, …) / fn.apply(obj, [args]) / fn.bind(obj)：this 就是 obj。call 立刻執行、參數逐一傳；apply 立刻執行、參數放陣列；bind 回傳新函式，this 永久綁定。
  3. obj.method()：this 是點號左邊的 obj。
  4. 單純的 fn()：嚴格模式（ES module、class 內）是 undefined，否則是全域物件。
  5. 箭頭函式：沒有自己的 this，用的是定義時外層的 this，call/bind 都改不了它。

最常出事的情境是「把方法當成值傳走」：const f = obj.method; f() 或 setTimeout(obj.method, 0) 或把方法傳給 onClick，點號消失了，this 也就跟著不見。

常見錯誤

class Timer {
  seconds = 0;
  start() {
    setInterval(function () { this.seconds++; }, 1000);   // this 不是 Timer
  }
}
// 把方法交給事件，this 變成 DOM 元素或 undefined
button.addEventListener("click", timer.start);

// 物件方法用箭頭函式：this 不是物件
const o = { n: 1, get: () => this.n };

正確做法

class Timer {
  seconds = 0;
  start() {
    setInterval(() => { this.seconds++; }, 1000);        // 箭頭函式沿用 start 的 this
  }
  onTick = () => { this.seconds++; };                    // class field + 箭頭：每個實例固定 this，可安全當 callback
}
button.addEventListener("click", () => timer.start());   // 或 timer.start.bind(timer)
const o = { n: 1, get() { return this.n; } };             // 物件方法用簡寫方法

經驗法則：物件方法、需要動態 this 的地方用一般函式；callback 內部要沿用外層 this 就用箭頭函式。Vue 3 的 <script setup> 與 composables 幾乎不用 this，這個問題在 Options API 與 class 裡才會出現。

實際應用

  • Array.prototype.slice.call(arguments), Math.max.apply(null, nums) 是舊式用法，現在用 [...nums] 與 Math.max(...nums)。
  • Vue Options API 的 methods 會被自動 bind 到元件實例，所以模板裡 @click="save" 能運作；但自己把方法傳進第三方函式庫時，仍要自己處理 this。

9.1　事件迴圈（Event Loop）

概念

JS 引擎一次只執行一段程式（單執行緒），但瀏覽器在旁邊提供計時器、網路、使用者事件等能力。事件迴圈是把「完成的工作」排隊送回主執行緒、一個一個執行的調度器。Java 對照：它像是單一執行緒的 ExecutorService 加上兩種優先級不同的佇列，但沒有鎖的問題，因為同一時間只會有一段程式在跑。

運作原理

一輪事件迴圈（簡化）

1. Call stack執行目前這個 task 的同步程式，直到堆疊清空
2. MicrotasksPromise.then、await 之後、queueMicrotask、MutationObserver。全部清空才繼續（包含執行中新加入的）
3. Render需要時：樣式計算、排版、繪製；requestAnimationFrame 在繪製前執行
4. Next task從 task queue 取下一個：setTimeout／setInterval 回呼、DOM 事件、postMessage、網路完成

1 → 2 → 3 → 4 → 1 → …

這是教學用的簡化模型。實際上瀏覽器有多個 task 佇列和優先級，渲染也不是每輪都做（通常約每 16ms 一次）。

  • 所以 setTimeout(fn, 0) 不是「立刻」：它是「至少等這一輪的 microtask 與（可能的）渲染做完，再排進下一個 task」，而且瀏覽器有最小延遲，巢狀超過 5 層會被拉到至少 4ms；背景分頁的計時器還會被降頻到約 1 秒一次。
  • 長任務會凍結頁面：同步的迴圈佔著 call stack，期間沒有事件處理、沒有渲染，使用者看到卡死。超過 50ms 就算 long task。解法是拆片（讓出主執行緒）、移到 Web Worker，或換演算法。
  • Microtask 餓死：microtask 會一直清到空，如果每個 microtask 又排一個新的 microtask，task 與渲染永遠輪不到。
  • async/await：await x 之前的程式同步執行；之後的程式變成 microtask，等 x 完成才排進去。async 函式永遠回傳 Promise。

先預測，再看結果

以下六題請先在腦中算出輸出順序，選好答案再按「執行驗證」。每題的程式是真的在瀏覽器裡跑一次，驗證的是引擎的實際行為，不是我的說法。

題 1：輸出順序？
  1. 同步程式先跑：A、D。
  2. 這個 task 結束後先清空 microtask：C。
  3. 最後才輪到下一個 task，也就是 setTimeout 的 B。
題 2：await 之後的程式什麼時候跑？
  1. 3 先印。
  2. 呼叫 f() 時，await 之前的部分是同步執行的，所以印 1。
  3. 遇到 await 就把後面的程式排進 microtask，f() 回傳 Promise，主程式繼續印 4。
  4. 同步結束後 microtask 執行：2。
題 3：在 microtask 裡又排 microtask，會怎樣？
microtask 佇列是清到空才離開的，執行中新加入的 microtask（p2）也會在同一輪被清掉，比任何 task（timeout）都早。這也是「microtask 餓死」的原理。
題 4：兩條 Promise 鏈交錯的順序？
第一輪 microtask：兩個第一層 then 依序執行（a1、b1），它們各自完成後才把第二層 then 排進佇列（a2、b2）。鏈上的每一步都要「等下一輪」，所以兩條鏈輪流前進。
題 5：then 裡 return 一個 Promise，會慢多少？
回傳一個 Promise（thenable）時，引擎要多花兩輪 microtask 去「吸收」它的結果，之後下一層 then 才能排進去。所以 x 會比只回傳普通值晚大約兩輪，落在 5 之後。這是少數你真的會在規格細節上踩到的地方：不要靠這種順序寫程式，要順序請明確串接。
題 6：計時器的先後與 async 函式的同步部分
async 函式在遇到第一個 await 之前都是同步的，所以 in async 比 end 早。接著是 microtask micro，然後計時器依「到期時間」排序：t0（0ms）先於 t10（10ms），與它們被註冊的順序無關。

常見錯誤

正確做法

    handle(items[i]);
    if (i % 200 === 199) await new Promise((r) => setTimeout(r, 0));
  }
}

// 2. Vue：等 DOM 更新用 nextTick，不要用猜的計時器

實際應用

  • Vue 的響應式更新是批次的：同一輪裡改多次狀態，只會在 microtask 中重新渲染一次，所以改了狀態之後 DOM 還沒變，要 await nextTick()。
  • Chrome DevTools 的 Performance 面板會用紅色標出 long task；requestIdleCallback／scheduler.yield()（支援度依瀏覽器而定）可用來讓出主執行緒。

9.2　Promise 深入：狀態、串接、並行與錯誤傳遞

概念

Promise 代表「一個尚未知道、將來會有結果的值」。三種狀態：pending（等待）→ fulfilled（成功）或 rejected（失敗）；一旦落定（settled）就不再改變。與 Java 的 CompletableFuture 很像，但 JS 的 Promise 是「急切的（eager）」：建立的當下函式就執行了，沒有辦法「還沒開始」。

運作原理

  • .then(onOk, onErr) 永遠回傳新的 Promise。回呼 return 的值成為新 Promise 的結果（若是 Promise 就會被吸收）；回呼 throw 則讓新 Promise rejected。
  • 錯誤傳遞：rejection 會沿著鏈往下找最近的 catch／onErr，途中的 then(onOk) 全部被略過；catch 處理完並正常回傳後，鏈就「恢復」成 fulfilled。想讓錯誤繼續往下傳，要在 catch 裡重新 throw。
  • .finally(fn): 無論成敗都執行，不接收參數，也不改變結果（除非它自己丟錯）。適合關閉 loading 狀態。
  • Unhandled rejection: 一個 rejected Promise 在該輪結束時沒有人處理，瀏覽器會觸發 unhandledrejection 事件、Node 預設會讓行程終止。常見成因：忘了 await、忘了 return 內層 Promise、在 forEach 的 async callback 裡丟錯。
組合器何時完成失敗時適合
Promise.all全部成功快速失敗：任一個失敗就立刻 reject（其他的仍在跑，只是結果被丟掉）互相依賴、缺一不可的資料
Promise.allSettled全部落定永不 reject；回傳每個 {status, value|reason}批次作業、要知道每一筆結果
Promise.race第一個落定（成或敗）第一個若是失敗就失敗逾時控制
Promise.any第一個成功全部失敗才 reject，帶 AggregateError多個備援來源取最快

順序執行 vs 並行：在迴圈裡 await 每一個，就是一個做完才做下一個（總時間相加）。互不依賴的工作應該先同時啟動，再一起等：await Promise.all(items.map(fn))。但同時送出上千個請求會打爆伺服器或瀏覽器的連線數，要限制並行數量。

常見錯誤

// 1. forEach 不會等 async callback

console.log("done");                          // 在任何 save 完成之前就印了

// 3. 互不依賴卻循序等待

// 4. Promise constructor 反模式：包了一層本來就是 Promise 的東西

正確做法

實際應用

  • 頁面初始化載入多個彼此獨立的 API：Promise.all；批次匯入每列各自成敗：allSettled；多個 CDN／備援端點：any。
  • 限制並行數（例如一次最多 5 個上傳）不在標準庫裡，常見做法是用小工具（如 p-limit）或自己寫工作池。
Vue / Nuxt 對照

Nuxt 的 useAsyncData、useFetch 會處理 pending／error 狀態與 SSR 去重；在 onMounted 裡自己 await 時，元件若已卸載，回來後再改狀態就是浪費或 bug，需要配合 9.4 的 AbortController 取消請求。

9.3　錯誤處理：同步、非同步與全域

概念

JS 沒有 checked exception，任何東西都能被 throw（字串、物件都行），但永遠丟 Error 物件，因為只有它帶有 stack，工具才能追蹤。常見內建型別：TypeError（對 undefined 取屬性、呼叫非函式）、ReferenceError（未宣告的變數）、RangeError（超出範圍、遞迴太深）、SyntaxError（JSON.parse 解析失敗也是它）。

運作原理

  • try/catch 只攔得住同步丟出的錯，以及 await 的 Promise 的 rejection。沒有 await 的 Promise、setTimeout 回呼裡的錯，都逃出 try/catch。
  • Error cause: new Error("載入失敗", { cause: err }) 保留原始錯誤，讓上層訊息友善、除錯時仍看得到底層原因。
  • 自訂錯誤類別: class HttpError extends Error 帶上 status 等欄位，上層可用 instanceof 分辨。要設定 this.name 才會顯示正確名稱。
  • finally: 清理資源與重設 loading 狀態；若 finally 裡 return 或 throw，會蓋掉 try／catch 的結果，所以不要在 finally 裡 return。
  • 全域兜底: window.addEventListener("error", …) 與 "unhandledrejection" 用來回報（Sentry 等）而不是用來處理；Vue 有 app.config.errorHandler 與元件層級的 onErrorCaptured，Nuxt 有 <NuxtErrorBoundary> 與 error.vue。

注意第 1 項：failing() 的 rejection 沒有人處理，所以最後由全域的 unhandledrejection 事件抓到（輸出的 [global] 那一行）。這就是「沒有 await 的 bug」在線上看起來的樣子：不是你的 catch，而是監控系統告訴你。

常見錯誤

try { risky(); } catch (e) { }                        // 吞掉錯誤：最糟的做法
throw "something failed";                             // 丟字串：沒有 stack
try { await a(); } catch (e) { throw new Error("failed"); }   // 遺失原始錯誤
try { fetch(url); } catch (e) { handle(e); }          // 忘了 await
catch (e) { console.log(e.message); }                 // e 不一定是 Error（可能是任何被丟出的值）

正確做法

try { await risky(); }
catch (e) {
  if (e instanceof HttpError && e.status === 404) return null;        // 只處理你預期的
  throw new Error("載入失敗", { cause: e });                  // 不認識的錯：保留 cause 再往上丟
} finally {
  loading.value = false;                                       // 清理放 finally
}

實際應用

  • 分層處理：底層（API client）把網路與 HTTP 錯誤轉成自訂錯誤；中層補上情境（加 cause）；最上層（頁面或全域）決定顯示 toast、導向登入頁還是回報。
  • 和 Spring Boot 的 @ControllerAdvice 一樣的想法：集中轉換、集中處理，不要每個呼叫點都寫一次 try/catch。Axios／ofetch 的 interceptor 就是前端的對應物。

小測驗

練習 9.3：retry 與 cause

實作 retry(fn, times)：最多嘗試 times 次。成功就回傳結果；全部失敗則 reject 一個 Error("failed after N attempts")，並把最後一次的錯誤放進 cause。

提示與參考答案

提示：迴圈裡 try／catch 並記住最後的錯誤；迴圈結束才丟出。

解析：return await fn() 在 try 內的 await 不能省略。寫成 return fn() 的話，rejection 會在 try 之外才發生，catch 就抓不到，重試因此失效。

9.4　Fetch 深入：HTTP 錯誤、取消、逾時與競態

概念

最重要的一件事：fetch 的 Promise 只在「網路層失敗」時 reject（斷線、DNS 失敗、被 CORS 擋下），HTTP 404／500 都是 fulfilled。你必須自己檢查 res.ok。這與 Axios 預設「非 2xx 就丟錯」不同，也與 Spring 的 RestTemplate 預設行為不同。

運作原理

  • Response: status, ok (200–299), headers; body 是串流，只能讀一次（res.json()、res.text() 擇一；要讀兩次用 res.clone()）。res.json() 本身也是 Promise，內容不是合法 JSON 會 reject 為 SyntaxError。
  • AbortController: const ctrl = new AbortController(); fetch(url, { signal: ctrl.signal }); ctrl.abort()。被取消的 fetch 會 reject 成 AbortError（DOMException，e.name === "AbortError"），那是「正常取消」而不是錯誤，不要顯示錯誤訊息。一個 controller 用過就不能再用，每次請求建立新的。
  • 逾時: fetch(url, { signal: AbortSignal.timeout(5000) }) 逾時時 reject 為 TimeoutError。要「手動取消 + 逾時」兩者並用：AbortSignal.any([ctrl.signal, AbortSignal.timeout(5000)])。fetch 預設沒有逾時，可能永遠等下去。
  • CORS: 跨來源請求由瀏覽器強制檢查，伺服器沒回對的 Access-Control-Allow-Origin，fetch 就是 reject 成 TypeError: Failed to fetch，而且 JS 看不到原因。非「簡單請求」（例如帶 Authorization 或 JSON content-type）會先送 OPTIONS 預檢。解法在伺服器端（Spring：@CrossOrigin 或 CorsRegistry），不是前端。
  • 競態條件（race condition）: 使用者輸入 "a" 再輸入 "ab"，兩個請求的回應順序不保證。若 "a" 的回應較慢、後到，就會蓋掉 "ab" 的結果，畫面顯示過期資料。解法：新請求出發時取消上一個（AbortController），或用請求序號只接受最新的。
關於可執行範例的誠實說明

本頁的範例跑在沙盒 iframe 裡：沒有你的後端、不能保證能連到任何網站，且 localStorage 不可用。所以 HTTP 狀態碼、JSON 解析等語意，用 new Response(…)（和 fetch 回傳的是同一種物件）與 data: URL 示範；「網路層失敗」用一個必然連不上的位址示範；「請求被取消」「競態」則用一個尊重 signal 的假 API 示範，邏輯與真實的 fetch 相同。要對真實伺服器實驗，請在本機啟動一個後端（或 npx http-server），再從你自己的頁面呼叫。

第 5 項的名稱在不同瀏覽器與環境可能是 TypeError（連線失敗）或 TimeoutError（逾時先到），這正是「不要靠錯誤訊息文字判斷，要看 e.name」的原因。

常見錯誤

const user = await res.json();                       // 404 時這裡拿到的是錯誤內容，卻被當成 user 使用

正確做法：一個小而完整的 fetch 包裝

class HttpError extends Error {
  constructor(status, body) { super("HTTP " + status); this.name = "HttpError"; this.status = status; this.body = body; }
}

async function api(path, { signal, json, ...init } = {}) {
  const res = await fetch(path, {
    ...init,
    signal: signal ? AbortSignal.any([signal, AbortSignal.timeout(8000)]) : AbortSignal.timeout(8000),
    headers: { ...(json ? { "Content-Type": "application/json" } : {}), ...init.headers },
    body: json ? JSON.stringify(json) : init.body,
  });
  if (!res.ok) throw new HttpError(res.status, await res.text().catch(() => ""));
  return res.status === 204 ? null : res.json();
}

// 在 Vue 中取消過期請求：watch 的 onCleanup 就是為此而設計
watch(query, async (q, _old, onCleanup) => {
  const ctrl = new AbortController();
  onCleanup(() => ctrl.abort());
  try { results.value = await api("/api/search?q=" + encodeURIComponent(q), { signal: ctrl.signal }); }
  catch (e) { if (e.name !== "AbortError") error.value = e; }
});

實際應用

  • 搜尋建議、自動完成、分頁與篩選：每次輸入都要處理「過期回應」。搭配 9.x 之後的 debounce（10.2）減少請求數量，兩者互補：debounce 減少發送，abort 處理已發送的。
  • Nuxt 的 useFetch／$fetch（底層是 ofetch）預設對非 2xx 丟錯，並且在 key 改變時自動取消前一個請求。TanStack Query 也有類似行為。這些是上面這些手工規則的封裝。

10.1　事件傳遞：捕獲、目標、冒泡與事件委派

概念

點擊一個按鈕時，事件不是只通知那個按鈕。它會沿著 DOM 樹走一趟：從 window 往下到目標（捕獲階段），到達目標本身（目標階段），再一路往上回到 window（冒泡階段）。沿途每個註冊了該事件的祖先都有機會處理它。

運作原理

  • addEventListener(type, fn) 預設監聽冒泡階段；{ capture: true } 則監聽捕獲階段。
  • event.target: 真正被點到的最內層元素（不變）。 event.currentTarget: 目前這個 listener 掛在哪個元素上（隨傳遞改變）。箭頭函式裡的 this 不會是它，請用 currentTarget。
  • stopPropagation(): 阻止事件繼續傳給下一個節點，但同一元素上的其他 listener 仍會執行； stopImmediatePropagation() 連同一元素上剩下的 listener 也不執行； preventDefault() 取消瀏覽器預設行為（連結跳轉、表單送出），但不影響傳遞。三者互相獨立。
  • 不會冒泡的事件: focus, blur, mouseenter, mouseleave, load, scroll （元素上）。改用會冒泡的 focusin／focusout／mouseover／mouseout。
  • listener 選項: once: true 執行一次後自動移除； passive: true 承諾不會呼叫 preventDefault()，讓瀏覽器不必等你就能捲動（touchstart／wheel 預設即為 passive）； signal 傳入 AbortSignal，一次移除多個 listener。

點擊 <button> 時，事件經過的路徑

capture ↓window → document → ul → li
targetbutton
bubble ↑li → ul → document → window

只要在 ul 掛一個冒泡 listener，就能處理所有 li 與 button 的點擊，這就是事件委派。

常見錯誤

// 1. 替每個子元素各掛一個 listener；之後新增的項目沒有 listener

// 3. e.target 可能是按鈕裡的 icon 或 span
list.addEventListener("click", (e) => { if (e.target.dataset.id) remove(e.target.dataset.id); });

// 4. 匿名函式無法移除
el.addEventListener("click", () => run());  el.removeEventListener("click", () => run());

正確做法

  const item = e.target.closest("[data-id]");          // closest 往上找，icon／span 也沒問題
  if (!item || !list.contains(item)) return;
  remove(item.dataset.id);
});

// 一次清掉所有 listener：搭配 AbortController

window.addEventListener("keydown", onKey, { signal: ctrl.signal });

實際應用

  • 大型清單、表格、動態內容：委派可以把 listener 數量從 N 個降到 1 個，也不用在項目增減時重新綁定。
  • 「點擊元件外部就關閉」：在 document 掛一個 listener，判斷 e.target 是否在元件內（root.contains(e.target)）。若有任何元素呼叫了 stopPropagation，這個功能就會壞掉。
Vue / Nuxt 對照

Vue 的事件修飾符就是這些選項的簡寫：@click.stop = stopPropagation()、.prevent = preventDefault()、.capture、.once、.passive、.self（只有 target 是自己時才觸發）。在 onMounted 掛全域 listener，要在 onUnmounted 移除，否則元件重複建立時會累積。

10.2　防抖（Debounce）與節流（Throttle）

概念

有些事件會以極高頻率觸發：input（每打一個字）、scroll、resize、mousemove。每次都做昂貴的事（呼叫 API、重新排版）會讓頁面卡頓。兩種節制方式：

防抖 Debounce節流 Throttle
意思「安靜下來之後」才執行一次：事件停止 N ms 才觸發「固定節奏」執行：每 N ms 最多一次
連續觸發時一直被延後，直到停下來過程中仍會定期執行
適合搜尋框輸入、表單即時驗證、視窗縮放結束後重算捲動位置追蹤、無限捲動判斷、拖曳中更新座標

運作原理

兩者都靠閉包保存計時器 id 或上次執行時間（8.1）。防抖的核心是「每次進來先清掉上一個計時器再重設」；節流的核心是「記住上次執行時間，還沒到就跳過（或排一個尾端執行）」。

function debounce(fn, ms) {
  let timer;
  function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);      // 保留 this 與最新參數
  }
  debounced.cancel = () => clearTimeout(timer);              // 元件卸載時要能取消
  return debounced;
}

function throttle(fn, ms) {
  let last = 0, timer, lastThis, lastArgs;
  const run = () => { last = Date.now(); timer = null; fn.apply(lastThis, lastArgs); };
  return function (...args) {
    lastThis = this; lastArgs = args;                        // 尾端執行用最新的參數
    const remaining = ms - (Date.now() - last);
    if (remaining <= 0) { clearTimeout(timer); run(); }     // 前緣：馬上執行
    else if (!timer) timer = setTimeout(run, remaining);     // 尾端：保證最後一次不會被吃掉
  };
}

常見錯誤

// 1. 每次事件都建立新的 debounce：每個都有自己的 timer，等於沒有防抖
input.addEventListener("input", (e) => debounce(search, 300)(e.target.value));
// Vue 模板同理：
// <input @input="debounce(search, 300)($event.target.value)">

// 2. 搜尋用 throttle：停下來時最後的輸入可能沒處理（沒有尾端）

// 3. 丟掉 this / 參數
const bad = (fn, ms) => { let t; return () => { clearTimeout(t); t = setTimeout(fn, ms); }; };

// 4. 元件卸載後 timer 仍會觸發，更新已經不存在的畫面

正確做法

// Vue 3 (script setup): 建立一次，卸載時取消

// 或用 VueUse：useDebounceFn、useThrottleFn、watchDebounced

實務上還要記得：防抖只減少「發送」次數，已經發出去的請求仍會有競態問題，所以要搭配 9.4 的 AbortController。scroll／resize 的視覺更新更適合用 requestAnimationFrame 節流；可見性判斷則用 IntersectionObserver，根本不需要監聽 scroll。

實際應用

  • 搜尋框：debounce 300ms + AbortController；表單即時檢查帳號是否重複：debounce 500ms。
  • 自動儲存草稿：debounce（停止輸入 1 秒後存）加上 beforeunload 或 visibilitychange 時立刻 flush。

10.3　ES Modules：import / export 真正的行為

概念

模組讓每個檔案擁有自己的作用域，只有 export 出去的東西別人才拿得到；別的檔案用 import 取用。Java 對照：它像 package + import，但模組是「執行期的物件」，而且同一個模組只會被求值一次，所有匯入者共用同一個實例（天然的單例，像 Spring 的 singleton bean）。

運作原理

  • Named vs default: export const a / import { a } 名稱必須一致（可用 as 改名）； export default x / import anything 每個模組最多一個，匯入時名字隨意。團隊多半偏好 named export：重構改名時工具可以追蹤，也不會出現同一個東西在不同檔案叫不同名字。
  • Live binding（活綁定）: 匯入的是「對原變數的唯讀參考」，不是值的拷貝。匯出端改了 export let count，匯入端立刻看到新值，但匯入端不能自己賦值。（與 CommonJS 的 require 拷貝值不同。）
  • 只求值一次: 無論被 import 幾次，模組頂層程式只執行一次，之後共用同一組匯出。
  • 靜態結構: import/export 必須在頂層、路徑是字串字面量，所以工具能在不執行程式的情況下分析依賴，做 tree shaking（移除沒被用到的匯出）。需要在執行時才決定或延後載入時，用動態 await import("./x.js")，它回傳 Promise，是路由 code splitting 的基礎。
  • 循環依賴: A 匯入 B、B 又匯入 A 時不會無限迴圈，但其中一方會在對方尚未完成求值時就開始跑；若在那一刻讀取尚未初始化的 const／let 匯出，會得到 ReferenceError（TDZ，見 8.1）。解法：把共用部分抽到第三個模組，或只在函式內（延後）才使用匯入。
  • 預設行為: 模組自動是嚴格模式；頂層 this 是 undefined；<script type="module"> 自動 defer；支援頂層 await。
必須用 http(s) 開啟，不能直接雙擊檔案

瀏覽器載入模組檔案要求 CORS，而 file:// 的來源是不透明的，所以直接用 file:// 開啟含有 import './x.js' 的頁面，Chrome 會報 CORS 錯誤。你一定要透過本機伺服器開啟，例如在資料夾裡執行 npx http-server 或 python -m http.server，再打開 http://localhost:8080。Vite 的開發伺服器（npm run dev）就是在替你做這件事。完整的多檔案範例見專案內的 examples/modules/，上面的互動範例則因為跑在沙盒 iframe 裡，用 Blob URL 模擬多個模組檔案。

最後一項：Blob URL 之間無法互相用相對路徑 import，要完整示範循環依賴請用專案裡的 examples/modules/（它有真實檔案：cycle-a.js 與 cycle-b.js，執行後會在 Console 印出 TDZ 錯誤與解法）。

Chapter 0The big picture: how a browser turns files into a screen

On the backend you are used to "a request comes in, the program handles it, a response goes out". The frontend lacks the server half: the browser takes the files and turns them into a screen by itself, then keeps running JavaScript on the user's machine. Roughly:

  1. 1. Parse HTMLbuild the DOM tree
  2. 2. Apply CSSwork out each element's style
  3. 3. Layoutwork out position and size
  4. 4. Paintdraw to the screen

When JavaScript changes the DOM or a style, the browser repeats steps 3 and 4.

The cascade and specificity: who wins

When several rules hit the same property, the one with higher specificity wins: inline style beats #id, which beats .class, attribute and pseudo-class, which beats a tag. At equal level, the later rule wins. !important beats everything, but it makes things hard to maintain later, so avoid it.

The box model

Every element is a box. From the inside out: content, padding, border and margin. By default width only counts the content, so adding padding and border makes the box wider, which is counterintuitive. That is why almost every project starts with:

*, *::before, *::after { box-sizing: border-box; }

With that, width includes padding and border.

Common units

  • px: fixed pixels. rem: relative to the root font size (16px by default), good for fonts and spacing.
  • %: relative to the parent. vw / vh: relative to the viewport width and height. dvh: a viewport height that follows the mobile address bar as it shows and hides.
  • fr: Grid only, a share of the remaining space.

Flexbox: one-dimensional layout

Set a container to display: flex and its children line up along one direction. The two properties you will adjust most: justify-content controls the main axis (horizontal by default) and align-items controls the cross axis (vertical by default).

  gap: 12px;                       /* space between children */
  justify-content: space-between;  /* distribute along the main axis */
  align-items: center;             /* align on the cross axis */
  flex-wrap: wrap;                 /* wrap when there is no room */
}

Chapter 5Async and browser APIs

JS runs on a single thread. When it hits something that has to wait, such as a network request or a timer, it hands the work to the browser, and the callback is queued for later. It only runs after the current code finishes. So the screen does not freeze while waiting, but you have to pay attention to "what runs first".

Java comparison There are no multithreading or lock problems, but there are ordering problems. A Promise is similar to CompletableFuture, and fetch is similar to HttpClient.

The order is: all synchronous code first, then Promise callbacks (microtasks), and setTimeout last (even 0 ms has to queue).

Promise and async / await

async function loadJson(url) {
  const res = await fetch(url);                       // wait for the network without freezing the page
  if (!res.ok) throw new Error("HTTP " + res.status); // fetch does not throw on 404 by itself
  return res.json();                                  // also a Promise
}

async function main() {
  try {
    const data = await loadJson("/data/taiwan.json");
    console.log(data.events.length);
  } catch (err) {
    console.error("Load failed", err);
  }
}
main();
Watch out await can only be used inside an async function (except at the top level of an ES module). fetch does not throw on 404 or 500, so check res.ok yourself.

Something every backend engineer runs into: CORS and file://

It is the browser that blocks it; curl and Postman are not affected. In Spring Boot, allow it with @CrossOrigin or a CORS configuration.

6.2　Forms and validation: let the browser enforce the rules

Concept

Browsers ship a built-in Constraint Validation system: declare the rules on the tags and the browser checks them before submit, blocks the submission and shows the message, with no JavaScript. JS steps in only for customisation.

AttributeEffect and gotchas
requiredMust not be empty
type="email|url|number|date"Format check; also picks the mobile keyboard and parsing. Phone numbers, postal codes and IDs are not "numbers" (leading zeros vanish): use type="text" inputmode="numeric"
patternA regex that must match the whole value (implicitly ^(?:…)$). Text-like inputs only; add a title that explains the rule
min / max / stepRange and step for number, date, range
minlength / maxlengthLength. minlength is only checked after the user has edited the value; a value set from code does not trigger it

How it works

  1. The submit flow: on a submit click or Enter the browser checks each control. If any is invalid it fires invalid on it, shows a bubble, and never fires submit. Only when everything is valid does your submit handler run.
  2. The API: every control has validity (valueMissing, typeMismatch, patternMismatch, tooShort, rangeUnderflow, customError …) and validationMessage. checkValidity() only returns a boolean (and fires invalid); reportValidity() also shows the bubble; setCustomValidity(msg) sets a custom error and only an empty string clears it.
  3. Styling: :invalid applies before the user has touched anything (a page full of red boxes on load). Use :user-invalid, which applies only after interaction.
  4. FormData: new FormData(form) collects every control that has a name, is not disabled and is checked. For same-name fields (checkbox groups) use getAll(); Object.fromEntries(fd) lets later values overwrite earlier ones. fetch(url, { method: 'POST', body: fd }) sends multipart; do not set Content-Type yourself or the boundary is lost.
  5. Client vs server validation: client-side validation is for experience (instant feedback, one less round trip); server-side validation is the security boundary, because anyone can bypass the frontend with curl. You need both. In Spring Boot use @Valid with Bean Validation (@NotBlank, @Email, @Size) and return 400 with field errors; map them back onto the fields. The two rule sets will drift; the server wins.
  6. Preventing double submits: in the submit handler disable the button and guard with a flag (Enter and the button take the same path); make the server idempotent too (idempotency key or a unique constraint), because users can still refresh, double-click or retry on a flaky network.

Try it: submit with everything empty and read the invalid reasons in the output; change the number input's min; remove the true capture argument from the invalid listener and see why events stop arriving.

Common mistake

<form>
  <input id="email" placeholder="Email">
  <input id="age" placeholder="Age">
  <button type="button" onclick="submitForm()">Submit</button>

Three problems: the button is type="button", so with more than one field Enter submits nothing and keyboard users are locked out; the hand-written check bypasses the validation and bubbles the browser already provides, and its rules can contradict the HTML attributes; and Number("") is 0, so an empty field slips through as a valid value.

The fix

Put the rules on attributes and listen to submit rather than the button's click, as in the demo above. When the server returns field errors, map them back with setCustomValidity and clear them as soon as the user types again:

const res = await fetch("/api/signup", { method: "POST", body: new FormData(form) });
if (res.status === 400) {
  const { errors } = await res.json();             // e.g. { email: "Already registered" }
  for (const [name, message] of Object.entries(errors)) {
    const input = form.elements[name];
    input.setCustomValidity(message);
    input.addEventListener("input", () => input.setCustomValidity(""), { once: true });  // never cleared = invalid forever
  }
  form.reportValidity();                           // show the first error bubble
}

In practice

  • For signup, checkout and admin CRUD forms most rules (required, format, length) need only attributes; reserve setCustomValidity for cross-field rules such as confirm-password or date ranges.
  • To submit programmatically use form.requestSubmit(), not form.submit(): the former runs validation and fires submit, the latter skips both.
Vue / Nuxt

Use <form @submit.prevent="onSubmit"> rather than @click on the button, so native validation and Enter-to-submit survive. The .prevent modifier is just e.preventDefault(). Form libraries mostly add a layer of rules and state on top of this native mechanism.

6.3　Accessibility: keyboard, focus and ARIA

Concept

Accessibility keeps your page usable for screen-reader users, keyboard-only users, people with low vision, and anyone temporarily limited (one hand full, bright sunlight). It also pays off for engineers: get semantics and the keyboard right and automated testing and SEO improve with them.

The first rule of ARIA

If a native element can do the job, do not use ARIA. ARIA only changes the accessibility tree and adds no behaviour: role="button" does not make a div focusable or make it respond to Enter. Native button, dialog, details and label already include all that.

How it works

Where names come from (simplified priority): aria-labelledby, then aria-label, then native sources (label, alt, button text, legend), then title. aria-labelledby points at visible text already on the page; aria-label is for controls with no visible text, such as icon buttons.

AttributePurpose
aria-expandedOn the trigger button: whether the region it controls is open or closed
aria-controlsPoints to the controlled region's id (helpful but unevenly supported; never rely on it alone)
aria-live / role="alert"Announces changes inside the region. The region must already exist in the DOM; only later changes are announced
aria-invalid + aria-describedbyMarks an invalid field and links it to its error message
aria-hidden="true"Removes from the accessibility tree. Never put it on a focusable element
tabindex0 joins the Tab order (custom widgets); -1 can only be focused with focus() (e.g. an error summary); never use positive values, they scramble the whole page's order

Keyboard and focus: Tab order equals DOM order, so rearranging the visual order with CSS (order, Grid) makes focus jump around. Never remove the :focus-visible style; outline: none is the most common accessibility bug.

Four rules for modals: focus moves in when it opens; Tab cannot escape to the background (focus trap); Esc closes it; on close focus returns to the button that opened it. Native <dialog>.showModal() handles all four (inert background, Esc, focus restoration), so prefer it.

Why do some pages work only with a mouse? Typical causes: click handlers on div/span that cannot take focus; menus that open only on :hover; removed outline so focus is invisible; hand-made dropdowns that ignore arrow keys; modals with no focus trap that drop focus back to the top of the page on close; drag-and-drop as the only way to act.

This is the disclosure pattern, right for site navigation and dropdown content. Do not reach for role="menu" just because it is called a menu: that is the desktop-application menu, and users then expect full arrow-key behaviour; failing to deliver it is worse than not claiming it.

Try it: after opening, Tab never reaches the page behind; Esc closes it and focus snaps back to the "Delete account" button. A button inside <form method="dialog"> closes the dialog and puts its value in returnValue. Putting the default focus on "Cancel" for a destructive action is deliberate.

A good error has four parts: a text message (never colour alone), aria-describedby linking it to the field, aria-invalid for the state, and focus moved to the first error. The role="alert" region exists from page load and only its text changes, which is what gets announced.

Common mistakes

<style>button:focus { outline: none }</style>                  <!-- keyboard users cannot see focus -->
<div aria-label="Close" onclick="closeDialog()">×</div>              <!-- aria-label on a generic element is often ignored -->
<button aria-label="Save">Save</button>             <!-- redundant, and drifts when the visible text changes -->

The fix

<style>button:focus-visible { outline: 3px solid #1f5fbf; outline-offset: 2px }</style>
<button type="button" aria-label="Close">×</button>      <!-- aria-label only where there is no visible text -->

In practice

  • A 30-second keyboard test before every merge: put the mouse aside and walk the main flow with Tab, Shift+Tab, Enter, Space and Esc. Lighthouse and axe catch only part of the problems; they cannot judge whether the focus order makes sense.
  • Complex widgets (combobox, tabs, date picker) are hard to get right by hand; teams usually adopt a headless library such as Headless UI or Reka UI, whose value is precisely handling the keyboard and ARIA details for you.
Vue / Nuxt

Vue's :aria-expanded="open" stringifies the boolean to "true"/"false". If a modal is moved to the body with <Teleport to="body"> (to dodge z-index trouble, see 7.1), verify that focus management still works after the DOM position changes.

7.1　Stacking context: why z-index: 9999 does nothing

Concept

z-index is not a global scoreboard. It is compared only within the same stacking context. Each context is a sealed universe: however large a child's z-index, the whole context is ranked as a single element in its parent context.

How it works

Any of these makes an element create a new stacking context (the common ones):

  • the root element html
  • position: relative/absolute with a z-index other than auto; position: fixed/sticky (always)
  • a flex or grid item with a non-auto z-index (no position needed)
  • opacity < 1、transform、filter、perspective、clip-path、mask
  • isolation: isolate、mix-blend-mode（非 normal）、will-change naming any of the above、contain: layout/paint

Inside one context, painting runs bottom to top roughly as: background, negative z-index children, in-flow blocks, floats, inline content, positioned elements with z-index: 0/auto, then positive z-index ascending. Ties go to the later DOM node.

The bug below: why the tooltip (9999) loses to content (2)

  • root stacking context
    • .sidebar z-index: 1 → new context
      • .tip z-index: 9999 (only ranks inside the sidebar)
    • .main z-index: 2 → new context

At the root level the contest is sidebar(1) vs main(2). The tip's 9999 is locked inside the sidebar and never meets main.

Try it: delete z-index: 1 from .sidebar and re-run. The tooltip surfaces because the sidebar is no longer a context, so the tip competes directly at root level.

Common mistakes

.card:hover { transform: translateY(-2px); }      /* silently turns every card into a new context */
.dropdown   { z-index: 99999; }                   /* inside .card, so the next card covers it */
.modal      { z-index: 2147483647; }              /* arms race: treats the symptom only */

The fix

  • Find the culprit: walk up from the covered element to the first ancestor that creates a context (DevTools → Elements → select the node and inspect transform, opacity, z-index, position in Computed, or walk up with getComputedStyle).
  • Remove the unneeded context, or put the z-indexes on the same level.
  • Isolate on purpose: give a component root isolation: isolate so its inner z-indexes neither leak out nor get affected, instead of relying on luck.
  • Lift overlays out of the component: attach modals, dropdowns and toasts to body, or use native <dialog> / the Popover API (the top layer ignores all contexts).
  • Define a z-index scale with CSS variables (--z-dropdown, --z-modal).
Vue / Nuxt

<Teleport to="body"> moves a component's DOM under body precisely to escape this stacking prison. UI-library dialogs and select panels usually teleport already; when your own overlay gets covered, suspect an ancestor's transform or overflow first.

7.2　Flexbox in depth: how space gets distributed

Concept

Flexbox is one-dimensional layout: it distributes spare (or missing) space along the main axis. You know justify-content and align-items; what actually decides each item's size is these three:

MeaningDefault
flex-basisstarting size before distribution; auto means look at width / contentauto
flex-growshare of any spare space0
flex-shrinkshrinks in proportion to (factor × basis) when space is short1

How it works

  1. Lay every item out at its flex-basis and compare the total with the container.
  2. Spare space: add it by flex-grow ratio. Shortage: subtract it by flex-shrink × basis ratio.
  3. Each item is clamped by min-width/max-width; clamped items drop out and the rest are recomputed.
The classic trap: min-width: auto

A flex item's min-width defaults to auto, meaning "no smaller than the content's minimum". For long words, URLs or nowrap text the minimum is the whole line, so the item cannot shrink and blows out the container. Two details: (1) if the item itself sets a non-visible overflow, auto resolves to 0, so the usual culprit is the outer flex item without overflow; an ellipsis child inside does not rescue it; (2) the fix is min-width: 0 on that flex item (the vertical equivalent is min-height: 0, the standard recipe for scrollable panes).

flex: 1 is shorthand for flex: 1 1 0% (grow 1, shrink 1, basis 0). A zero basis means everyone starts from 0 and splits equally, so several flex:1 items come out equal-width, whereas flex: auto (1 1 auto) starts from content width and ends unequal.

Common mistake

.list-item { display: flex; gap: 8px; }
.list-item .body { flex: 1; }                       /* outer flex item: no min-width:0 */
.list-item .name { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
/* .body's minimum width = the full text width of .name → a long file name pushes the row out of the viewport and the ellipsis never appears */

The fix: the classic admin layout

.admin { display: flex; min-height: 100vh; }
.sidebar { flex: 0 0 240px; }                      /* fixed width, no grow or shrink */

7.3　Grid in depth: two-dimensional layout and auto-wrapping

Concept

How it works

  • fr：shares of the leftover space. 1fr 2fr is 1:2. Note that 1fr is really minmax(auto, 1fr), so long content can blow it out; use minmax(0, 1fr) (same idea as flex's min-width: 0).

  • gap replaces margin hacks; justify-items / align-items align items inside their cell; justify-content / align-content align the whole track set inside the container (only matters when the container is larger than the tracks).

Chapter 8　AdvancedJS core mechanics: scope, references, this, prototypes

Coming from Java, four things trip people up in JavaScript: where a variable lives (scope and closures), what assignment actually copies (value vs reference), who this points to, and the fact that a "class" is not quite a class. Each section compares with Java.

8.1　Scope and closures

Concept

Scope decides where a name is visible. JS uses lexical scope: visibility depends on where the code is written, not where it is called. A closure is a function together with the scope it was created in: even after leaving that place, it can still read and write those outer variables.

How it works

  • Every time a function or block runs, the engine creates an environment holding names and values plus a link to the outer environment. Variable lookup walks that chain outward; if nothing is found you get a ReferenceError.
  • var：function-scoped, hoisted and initialised to undefined. let / const: block-scoped, hoisted into the temporal dead zone (TDZ) where access before the declaration throws ReferenceError. const only forbids reassignment; the object it holds stays mutable.
  • A closure keeps the variable itself, not a snapshot of its value. So several functions can share one state; and for (let i…) is safe because each iteration gets its own fresh i.
  • Java comparison: a Java lambda can capture only effectively-final locals (a copy of the value); a JS closure can mutate the captured variable. In Java you would need an AtomicInteger or a field.

Common mistakes

// 1. var in a loop plus async
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);   // 3 3 3

// 2. a closure pins a large object so it can never be freed
function attach(el) {
  const hugeData = loadHugeData();
  el.addEventListener("click", () => console.log(hugeData.length));  // hugeData lives as long as the listener
}

The fix

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);   // 0 1 2

function attach(el) {
  const length = loadHugeData().length;                // keep only what you need
  el.addEventListener("click", () => console.log(length), { once: true });
}

In practice

  • Private state, factory functions, once(fn), memoization and debounce/throttle (see 10.2) are all closures.
  • React hooks and Vue's setup() and composables are built on closures: setup runs once and the functions declared inside keep reaching the same ref through the closure.
Vue / Nuxt

Reading a "stale value" in a watch or handler is usually a closure over a value captured earlier: after const { count } = reactive(state), count is a plain number detached from the state. Use toRefs or read state.count directly.

8.2　Value vs reference: what actually gets copied

Concept

Primitives (number, string, boolean, null, undefined, symbol, bigint) copy their value on assignment. Objects (arrays, functions, Date, Map included) copy a reference: two variables point at the same object. Function arguments are always pass-by-value, but an object variable's value is a reference, exactly the Java behaviour.

How it works

TechniqueDepthCaveats
{...obj} / [...arr] / Object.assignshallow: first level onlynested objects are still shared

Three more traps: === on objects compares references, so {} === {} is false; const freezes the binding, not the content; and Object.freeze is shallow.

How Vue's reactive and ref treat references

  • reactive(obj) returns a Proxy of obj, not a copy; writing through the proxy mutates the original and triggers updates. Replacing a reactive object wholesale (state = {...}) loses reactivity; mutate fields or use Object.assign(state, next).
  • ref(x) wraps the value in { value } because a primitive cannot be "referenced". Templates unwrap it automatically; in script you write .value.
  • For a point-in-time snapshot (API call, saved draft, structuredClone) get the original with toRaw(state) and copy that: structuredClone(toRaw(state)).

8.3　this, arrow functions, call / apply / bind

Concept

In Java this is always the current object. In JS this is decided at call time (arrow functions excepted): the same function called differently gets a different this.

How it works: the rules (highest priority first)

  1. new Foo()：this is the freshly created object.
  2. fn.call(obj, …) / fn.apply(obj, [args]) / fn.bind(obj)：this is obj. call invokes now with arguments listed; apply invokes now with an array; bind returns a new function with this fixed for good.
  3. obj.method()：this is whatever is left of the dot.
  4. A bare fn(): undefined in strict mode (ES modules, class bodies), otherwise the global object.
  5. Arrow functions：have no this of their own; they use the enclosing one from where they were defined, and call/bind cannot change it.

The classic trouble is passing a method around as a value: const f = obj.method; f(), setTimeout(obj.method, 0), or handing it to onClick. The dot disappears, and this goes with it.

Common mistakes

  seconds = 0;
  start() {

  }
}

// arrow as an object method: this is not the object

The fix

  seconds = 0;
  start() {
    setInterval(() => { this.seconds++; }, 1000);        // the arrow reuses start's this
  }
  onTick = () => { this.seconds++; };                    // class field + arrow: fixed per instance, safe as a callback
}
button.addEventListener("click", () => timer.start());   // or timer.start.bind(timer)
const o = { n: 1, get() { return this.n; } };             // use method shorthand on objects

Rule of thumb: use regular functions for object methods and wherever a dynamic this is wanted; use arrows for callbacks that should keep the outer this. Vue 3 <script setup> and composables almost never use this; the problem lives in the Options API and in classes.

In practice

  • Array.prototype.slice.call(arguments), Math.max.apply(null, nums) are the old idioms; today use [...nums] and Math.max(...nums).
  • Vue Options API methods are auto-bound to the component instance, which is why @click="save" works; when you pass a method into a third-party library you still handle this yourself.

9.1　The event loop

Concept

The JS engine runs one piece of code at a time (single thread) while the browser supplies timers, networking and user events on the side. The event loop is the scheduler that queues finished work and feeds it back to the main thread one item at a time. Java comparison: a single-thread ExecutorService with two queues of different priority, and no locking issues because only one piece of code ever runs at a time.

How it works

One turn of the event loop (simplified)

1. Call stackruns the current task's synchronous code until the stack is empty
2. MicrotasksPromise.then, code after await, queueMicrotask, MutationObserver. Drained completely (including ones added meanwhile) before moving on
3. Renderwhen needed: style, layout, paint; requestAnimationFrame runs just before painting
4. Next tasktake the next item from the task queue: setTimeout/setInterval callbacks, DOM events, postMessage, network completion

1 → 2 → 3 → 4 → 1 → …

A teaching model. Real browsers have several task queues with priorities, and rendering does not happen every turn (typically about every 16ms).

  • So setTimeout(fn, 0) is not "immediately": it means "after this turn's microtasks and any rendering, in a later task", browsers impose a minimum delay (clamped to 4ms past 5 nesting levels), and background tabs throttle timers to about once per second.
  • Long tasks freeze the page: a synchronous loop holds the call stack, so nothing handles events or renders and the user sees a hang. Over 50ms counts as a long task. The cures are chunking (yield to the main thread), a Web Worker, or a better algorithm.
  • Microtask starvation: microtasks drain until empty, so if each one schedules another, tasks and rendering never get a turn.
  • async/await：code before await x runs synchronously; the rest becomes a microtask queued when x settles. An async function always returns a Promise.

Predict first, then check

For each of the six questions work out the output order in your head, pick an answer, then press "Run to verify". The code really runs in your browser, so you are checking the engine, not my claims.

Q1: what is the output order?
  1. Sync code first: A, D.
  2. When this task ends, microtasks drain first: C.
  3. Only then comes the next task, the setTimeout callback B.
Q2: when does the code after await run?
  1. 3 prints first.
  2. Calling f() runs everything before await synchronously, so 1 prints.
  3. At await the rest is queued as a microtask and f() returns a Promise; the main flow continues with 4.
  4. After the sync part ends the microtask runs: 2.
Q3: what happens when a microtask schedules another microtask?
The microtask queue is drained until empty, so a microtask added mid-drain (p2) also runs in the same turn, before any task (timeout). It is also why microtask starvation is possible.
Q4: how do the two Promise chains interleave?
First drain: the two first-level thens run in order (a1, b1); only when each finishes is its second-level then queued (a2, b2). Every step in a chain waits for the next round, so the two chains advance in turns.
Q5: how much slower is returning a Promise from then?
Returning a Promise (a thenable) costs the engine two extra microtask rounds to "absorb" its result before the next then can be queued. So x lands about two rounds later than with a plain value, after 5. This is one of the few places where spec details really bite: do not write code that depends on such ordering; chain explicitly when order matters.
Q6: timer ordering and the synchronous part of an async function

9.2　Promises in depth: states, chaining, concurrency and error propagation

Concept

A Promise represents a value not yet known. Three states: pending → fulfilled or rejected; once settled it never changes. It is close to Java's CompletableFuture, but JS Promises are eager: the executor runs the moment you create one, there is no "not started yet".

How it works

  • .then(onOk, onErr) always returns a new Promise. The callback's return value becomes its result (a returned Promise is absorbed); a thrown error rejects it.
  • Error propagation：a rejection travels down the chain to the nearest catch/onErr, skipping every then(onOk) on the way; after a catch returns normally the chain "recovers" to fulfilled. To keep the error travelling, rethrow in the catch.
  • .finally(fn): runs either way, receives no argument and does not change the outcome (unless it throws). Ideal for clearing a loading flag.
  • Unhandled rejection: a rejected Promise nobody handled by the end of the turn triggers the browser's unhandledrejection event and, by default, terminates a Node process. Typical causes: a missing await, a missing return of an inner Promise, an error thrown in an async callback inside forEach.

9.3　Error handling: sync, async and global

Concept

JS has no checked exceptions and anything can be thrown (strings, objects), but always throw an Error object, since only it carries a stack for tooling. Built-in types you will meet: TypeError (property of undefined, calling a non-function), ReferenceError (undeclared variable), RangeError (out of range, runaway recursion), SyntaxError (including a failed JSON.parse).

How it works

  • try/catch catches only synchronous throws and rejections of awaited Promises. Errors from a Promise without await, or inside a setTimeout callback, escape the try/catch.
  • Error cause: new Error("載入失敗", { cause: err }) keeps the original error: friendly message on top, root cause still visible when debugging.
  • Custom error classes: class HttpError extends Error carry fields such as status, and callers branch with instanceof. Set this.name so the right name shows.
  • finally: for cleanup and resetting loading flags; a return or throw inside finally overrides the try/catch result, so do not return from finally.
  • Global safety nets: window.addEventListener("error", …) and "unhandledrejection" are for reporting (Sentry and similar), not handling; Vue has app.config.errorHandler and component-level onErrorCaptured, Nuxt has <NuxtErrorBoundary> and error.vue.

Note item 1: the rejection of failing() is handled by nobody, so the global unhandledrejection event catches it (the [global] line). That is what a missing-await bug looks like in production: not your catch, but your monitoring telling you.

}

In practice

  • Layer it: the lowest layer (API client) turns network and HTTP failures into custom errors; the middle adds context (with cause); the top (page or global) decides between a toast, a login redirect or a report.
  • The same idea as Spring Boot's @ControllerAdvice: convert and handle centrally instead of writing try/catch at every call site. Axios/ofetch interceptors are the frontend counterpart.

9.4　Fetch in depth: HTTP errors, cancellation, timeouts and races

Concept

The most important fact: fetch's Promise rejects only on network-level failure (offline, DNS error, CORS block); an HTTP 404 or 500 still fulfils. You must check res.ok yourself. This differs from Axios (which throws on non-2xx by default) and from Spring's RestTemplate.

How it works

  • Response: status, ok (200–299), headers; the body is a stream and can be read only once (res.json() or res.text(); use res.clone() to read twice). res.json() is itself a Promise and rejects with SyntaxError on invalid JSON.
  • AbortController: const ctrl = new AbortController(); fetch(url, { signal: ctrl.signal }); ctrl.abort(). An aborted fetch rejects with AbortError (a DOMException, e.name === "AbortError"), which is a normal cancellation, not an error to show. A controller is single-use; make a new one per request.
  • Timeout: fetch(url, { signal: AbortSignal.timeout(5000) }) rejects with TimeoutError on expiry. To combine manual cancel and timeout: AbortSignal.any([ctrl.signal, AbortSignal.timeout(5000)]). fetch has no default timeout and can wait forever.
  • CORS: cross-origin requests are checked by the browser; without the right Access-Control-Allow-Origin from the server, fetch rejects with TypeError: Failed to fetch and JS cannot see why. Non-"simple" requests (for example with Authorization or a JSON content type) trigger an OPTIONS preflight. The fix lives on the server (Spring: @CrossOrigin or CorsRegistry), not in the frontend.
  • Race condition: a user types "a" then "ab"; response order is not guaranteed. If the slow "a" response arrives last it overwrites the "ab" result and the screen shows stale data. The fix: abort the previous request when a new one starts (AbortController), or tag requests with a sequence number and accept only the latest.
An honest note about the runnable examples

The examples on this page run in a sandboxed iframe: no backend of yours, no guarantee of reaching any website, and no localStorage. So HTTP status codes and JSON parsing are demonstrated with new Response(…) (the same kind of object fetch returns) and data: URLs; "network-layer failure" with an address that cannot connect; and cancellation and races with a fake API that honours signal, with the same logic as real fetch. To experiment against a real server, start a local backend (or npx http-server) and call it from your own page.

Item 5 may print TypeError (connection failure) or TimeoutError (the timeout fired first) depending on browser and environment, which is exactly why you branch on e.name rather than on message text.

10.1　Event propagation: capture, target, bubble and delegation

Concept

Clicking a button does not notify only that button. The event makes a trip through the DOM tree: down from window to the target (the capture phase), at the target itself (the target phase), then back up to window (the bubble phase). Every ancestor with a listener for that event gets a chance along the way.

How it works

  • addEventListener(type, fn) listens in the bubble phase by default; { capture: true } listens in the capture phase.
  • event.target: the innermost element actually hit (constant). event.currentTarget: the element the current listener is attached to (changes during propagation). this inside an arrow function will not be it; use currentTarget.
  • stopPropagation(): stops the event from reaching the next node, but other listeners on the same element still run; stopImmediatePropagation() also stops the remaining listeners on the same element; preventDefault() cancels the browser's default action (link navigation, form submit) but does not affect propagation. The three are independent.
  • Events that do not bubble: focus, blur, mouseenter, mouseleave, load, scroll (on elements). Use the bubbling focusin/focusout/mouseover/mouseout instead.
  • Listener options: once: true removes itself after one run; passive: true promises never to call preventDefault(), so the browser can scroll without waiting for you (touchstart/wheel are passive by default); signal takes an AbortSignal to remove many listeners at once.

The path of a click on the <button>

capture ↓window → document → ul → li
targetbutton
bubble ↑li → ul → document → window

A single bubble listener on the ul can handle clicks on every li and button; that is event delegation.

Common mistakes

// 3. e.target may be an icon or span inside the button

// 4. an anonymous function cannot be removed

The fix

10.2　Debounce and throttle

Concept

Some events fire at very high frequency: input (every keystroke), scroll, resize, mousemove. Doing something expensive each time (an API call, a re-layout) makes the page janky. Two ways to rein it in:

DebounceThrottle
Meaningrun once "after things go quiet": N ms after the last eventrun "at a steady pace": at most once per N ms
During a burstkeeps getting postponed until the burst endsstill fires periodically during the burst
Fitssearch input, live validation, recompute after a resize endsscroll tracking, infinite-scroll checks, updating coordinates while dragging

How it works

Both rely on a closure holding a timer id or the last-run time (8.1). Debounce's core is "clear the previous timer and set a new one on every call"; throttle's core is "remember the last run time and skip (or schedule a trailing run) when it is too soon".

function debounce(fn, ms) {
  let timer;
  function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);      // keep this and the latest arguments
  }
  debounced.cancel = () => clearTimeout(timer);              // must be cancellable on unmount
  return debounced;
}

function throttle(fn, ms) {
  let last = 0, timer, lastThis, lastArgs;
  const run = () => { last = Date.now(); timer = null; fn.apply(lastThis, lastArgs); };
  return function (...args) {
    lastThis = this; lastArgs = args;                        // the trailing run uses the latest arguments
    const remaining = ms - (Date.now() - last);
    if (remaining <= 0) { clearTimeout(timer); run(); }     // leading: run immediately
    else if (!timer) timer = setTimeout(run, remaining);     // trailing: the final call is never lost
  };
}

Common mistakes

// 1. creating a new debounce on every event: each has its own timer, so nothing is debounced

// same in a Vue template:
// <input @input="debounce(search, 300)($event.target.value)">

// 2. using throttle for search without a trailing call: the final input may never be processed

// 3. dropping this / arguments
const bad = (fn, ms) => { let t; return () => { clearTimeout(t); t = setTimeout(fn, ms); }; };

// 4. timers still firing after the component unmounts

The fix

input.addEventListener("input", (e) => onInput(e.target.value));

// Vue 3 (script setup): create once, cancel on unmount

// or VueUse: useDebounceFn, useThrottleFn, watchDebounced

In practice, remember that debounce only reduces how many requests are sent; requests already sent still race, so pair it with 9.4's AbortController. Visual updates on scroll/resize are better throttled with requestAnimationFrame, and visibility checks with IntersectionObserver, which needs no scroll listener at all.

In practice

  • Search box: debounce 300ms + AbortController; live "is this username taken" check: debounce 500ms.
  • Draft autosave: debounce (save one second after typing stops) plus an immediate flush on beforeunload or visibilitychange.

10.3　ES Modules: how import / export really behave

Concept

Modules give every file its own scope; only what it exports is reachable, and other files import it. Java comparison: like packages plus import, except a module is a runtime object and is evaluated only once, with every importer sharing that single instance (a natural singleton, like a Spring singleton bean).

How it works

  • Named vs default: export const a / import { a } names must match (rename with as); export default x / import anything at most one per module, any name on import. Teams mostly prefer named exports: refactoring tools can track them and the same thing does not get different names in different files.
  • Live bindings: an import is a read-only reference to the original variable, not a copy of its value. When the exporter changes export let count the importer sees the new value immediately, but cannot assign to it. (Unlike CommonJS require, which copies.)
  • Evaluated once: however many times it is imported, the module's top-level code runs once and the exports are shared.
  • Static structure: import/export must be top-level with a string-literal specifier, so tools can analyse dependencies without running the code and tree-shake unused exports. For runtime or deferred loading use dynamic await import("./x.js"), which returns a Promise and underlies route-level code splitting.
  • Circular imports: A 匯入 B、B 又匯入 A do not loop forever, but one side starts running before the other has finished evaluating; reading an uninitialised const/let export at that moment throws ReferenceError (TDZ, see 8.1). Fix it by extracting the shared part into a third module, or by using the import only later, inside functions.
  • Defaults: modules are strict by default; top-level this is undefined; <script type="module"> is deferred automatically; top-level await is supported.
It needs http(s); double-clicking the file will not work

Browsers load module files under CORS rules, and a file:// origin is opaque, so opening a page with import './x.js' directly via file:// makes Chrome report a CORS error. Always serve it locally, e.g. run npx http-server or python -m http.server in the folder and open http://localhost:8080. Vite's dev server (npm run dev) does exactly this for you. A complete multi-file example is in the project at examples/modules/; the interactive demos here run in a sandboxed iframe, so they simulate separate module files with Blob URLs.

On the last item: Blob URLs cannot import each other by relative path, so for a full circular-import demo use examples/modules/ in the project (real files cycle-a.js and cycle-b.js; run it and the Console prints the TDZ error and the fix).

  • In Node and Spring-hosted frontend builds, "type": "module" in package.json makes .js files ESM; require and module.exports are the older CommonJS.
